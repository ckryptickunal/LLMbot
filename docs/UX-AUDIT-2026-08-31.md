# End-to-end UX/UI audit — 2026-08-31

> **Status: most of this is fixed.** The findings below are kept as written, because the record
> of what was wrong is worth more than a tidied list. A `**FIXED**` note follows each item that
> has been addressed and verified; anything without one is still open and is collected in
> [What is still open](#what-is-still-open) at the end.

**Method.** Every file in `Sources/BotHarness/` and the design layer read in full at commit
`b8009b1` (plus the uncommitted mascot/tokens/conversation changes on disk); claims about
wiring verified by grep; the signed bundle launched five times against scratch homes built to
exercise every message type, name length, channel shape, and empty state, and screenshotted.
Nothing was fixed in this session; this is the problem list, ordered by severity. Each item
says how it was established: **(code)** read directly, **(live)** observed in a screenshot,
**(grep)** confirmed by search, **(likely)** inferred with stated mechanism but not exercised.

A caveat on line references: three sessions are editing this tree concurrently, so items cite
symbols rather than line numbers.

## 1. Critical — data loss, safety, or a dead end the user cannot leave

**1.1 The composer destroys messages when nothing is selected.** **FIXED** — the column now shows an empty state with a New-bot action and no composer at all; `send` also clears the draft only after the runner accepts it. Verified in the running app.

> *Original finding:* (code + live)
`ConversationView` builds `Composer(conversationID: store.selection ?? UUID())`. With an empty
roster the column shows a fully live-looking composer ("Ask anything", attach button, send
button) — screenshotted — but `send()` clears the draft *first* and `BotRunner.send` then
guards `store.conversation(id)` and silently returns. The typed message is gone. Same for
`Store.append`, which silently drops messages to unknown conversations.

**1.2 Editing one bot's settings can silently edit a different bot.** **FIXED** — the local `draft` copy is gone — every control reads and writes the live record — and the pane carries `.id(bot.id)`.

> *Original finding:* (code)
`BotSettingsPane` keeps `@State private var draft: Bot?` and renders `draft ?? bot`. The pane's
structural identity never changes and `draft` is never reset when the selection changes, so:
select bot A, type in any field, select bot B — the pane still shows A's data over B, and the
next keystroke writes A's record while the user believes they are editing B. There is no
`.id(bot.id)` and no `onChange(of: bot?.id)` reset.

**1.3 Two agent runs can execute concurrently in one conversation, and one becomes unstoppable.** **FIXED** — `BotRunner.canSend` gates both Return and the send button; the placeholder says the bot is working.

> *Original finding:*
(code) `BotRunner.send` never checks `isRunning`. Sending while a run is active overwrites
`loops[id]` and `tasks[id]`; the first loop's `Task` keeps running (it holds its own strong
references), both loops interleave messages into the same transcript, Stop only cancels the
newer one, and when the *first* finishes, its completion handler nils out the *second* run's
handles. The composer even invites this: while running it shows a Stop button, but Return still
sends.

**1.4 Approval cards go dead after a relaunch or a stop, and look alive.** **FIXED** — `Store.reconcileInterruptedWork` settles them at launch and `settleOpenWork` at stop; answering into a dead loop resolves the card instead of doing nothing. ADR 0013, tested.

> *Original finding:* (code + live)
`BotRunner.answer` begins `guard let loop = loops[conversationID] else { return }`. After the
app relaunches (or after Stop), a pending approval card still renders its three enabled buttons
— screenshotted — and clicking any of them does *nothing*: no state change, no message, no
explanation. The card can never be answered or dismissed. Nothing on launch reconciles
persisted `approval` messages whose run no longer exists.

**1.5 Stopping a run mid-approval wedges the "waiting" state forever.** **FIXED** — `stop()` clears `awaiting` for the conversation.

> *Original finding:* (code)
`stop()` clears `tasks` and `loops` but not `awaiting`. `Composer.mascotState` checks
`awaiting` first, so the mascot hops/waits permanently for a question that can no longer be
answered, until some future send happens to reset it.

**1.6 "Always allow this" is permanent and invisible-in-practice.** **FIXED** — Settings → Permissions can now add, edit and remove rules, and the approval card offers Never as well as Always. Tested.

> *Original finding:* (code)
The approval card's "Always allow this" writes a `PermissionRule` — and the Permissions tab in
Settings is **read-only**: `RuleRow` has no edit, no delete, and there is no add-rule control
anywhere, despite the tab's own copy instructing "Write one short rule per action." One
mis-click on "Always allow this" grants a standing permission that cannot be revoked from the
interface at all (only by hand-editing `state.json`). This is the safety-critical half of the
permission system with no management surface.

**1.7 A bot that needs you while the app is in the background is completely silent.** **FIXED** — `Notifier` posts on approval, finish and failure, honours `bot.notifies`, asks for permission at first need, and stays quiet when you are already looking at that conversation.

> *Original finding:* (code)
There is no notification path of any kind: `bot.notifies` is stored and toggled in the UI but
read by nothing (grep: zero readers); no `UNUserNotification*` anywhere; no Dock badge; no
sound. The one signal that exists — the mascot's two attention hops — is driven by a
`TimelineView` that is *paused when the app is inactive*, which is precisely when a
long-running bot hits an approval. The headline use-case (delegate work, go do something else)
ends with the bot blocked indefinitely and the user never told. The settings toggle promising
"Get notified when this bot finishes or needs input" is currently a lie.

**1.8 Quitting can lose the last ~400 ms of state.** **FIXED** — the app writes synchronously on terminate and flushes on resign-active. Tested.

> *Original finding:* (code + grep)
Every mutation goes through `scheduleSave()` (400 ms debounce). `saveNow()` is called only by
that debounce and by first-run seeding; there is no `applicationShouldTerminate`, no
`willTerminate` observer, no scene-phase save. Answer an approval or edit a persona and hit ⌘Q
within the window and the change is silently gone — worst on the approval, whose *loop* got
the answer but whose *record* did not.

**1.9 No way to delete a bot. At all.** **FIXED** — roster context menu and a button in bot settings, both behind a confirmation, both cancelling the bot's running work first and repairing the selection. Tested.

> *Original finding:* (code + grep + live)
`Store.deleteBot` exists and is called from nowhere. No context menu on roster rows, no button
in bot settings, no menu item, no Edit → Delete. Meanwhile ⌘N and both "+"/"New bot" buttons
create a persistent bot instantly. During the audit the user's stray ⌘N presses created two
junk "New Bot" rows — screenshotted — which are now permanent residents of that roster.
`deleteBot` also never fixes `selection`, so the first caller to wire it up will strand the UI
on a deleted conversation.

**1.10 The default workspace is the whole Desktop, and no surface ever says so.** **FIXED** — bot settings shows the folder, explains what it means, and offers Choose/Reset; `Bot.defaultWorkspace` is now the single definition the runtime also uses.

> *Original finding:* (code)
`BotRunner.contract` defaults `workspace` to `~/Desktop` and grants
`writable: [workspace/**]` plus `granted: [files.write, shell.exec, computer.control, …]`.
`Bot.workspace` is settable in the model and shown/edited **nowhere** — bot settings has no
folder picker and no read-only display of the scope. The autonomy chip offers "Work — works in
its folder" without any way to know or choose what "its folder" is. A bot on "Work" autonomy
may modify anything on the Desktop without asking, and the user was never shown that boundary.

## 2. Major UX — broken flows, missing affordances, misdirection

**2.1 Return sends mid-composition for CJK and other IME users.** **FIXED** — Return is ignored while the focused editor has marked text.

> *Original finding:* (likely, mechanism certain)
`onKeyPress(.return, phases: .down)` intercepts the Return that a Japanese/Chinese/Korean input
method needs to *confirm the composition*, so the message sends with the candidate text in an
indeterminate state. Needs verifying with an IME, but the interception happens before the
input method by construction. No alternative (⌘Return) exists either.

**2.2 One shared draft bleeds across conversations.** **FIXED** — drafts are per conversation, held in `UIState`.

> *Original finding:* (code)
`draft` is a single `@State` on `ConversationView`. Type to bot A, click bot B: the half-typed
message is now sitting in B's composer, one Return away from going to the wrong bot. Standard
messenger behaviour is a per-conversation draft.

**2.3 The roster gives no sign a bot needs you, is running, or failed.** **FIXED** — rows carry a status word (Needs you / Running) and an unread dot backed by `Conversation.lastReadAt`.

> *Original finding:* (code + live)
A row whose last message is "Needs your approval — …" renders in exactly the secondary style of
any idle preview — no badge, no colour, no dot, no bold. There are no unread markers at all, so
activity in an unselected conversation is invisible. For a multi-bot product whose core loop is
"delegate and glance", the roster answers none of the glance questions. (The design system even
defines the vocabulary for this — `DS.Status.awaitingApproval`, "Needs you" — unused here.)

**2.4 No keyboard access to the two main lists.** **FIXED** — both are `List(selection:)` now — arrow keys, type-select, focus ring, VoiceOver rows.

> *Original finding:* (code)
The roster and the Activity window's run list are `ScrollView` + `LazyVStack` +
`onTapGesture`. No arrow-key selection, no type-to-select, no focus, no Return-to-open. A
`List` would have provided all of it. The app cannot be driven without a mouse.

**2.5 Below ~600 pt of width the roster vanishes with no way back.** **FIXED** — the sidebar toggle is back, the roster remembers who closed it, and ⌥⌘1 reopens it.

> *Original finding:* (code)
`RootView.adapt` sets `columns = .detailOnly` when the window is narrow, and the sidebar toggle
was explicitly removed (`.toolbar(removing: .sidebarToggle)`). Until the user physically widens
the window there is no path to any other conversation. Related: `adapt` also force-reopens the
sidebar on every resize (`columns = .all`), overriding a sidebar the user deliberately
collapsed — the exact behaviour the inspector code goes out of its way to avoid, applied
inconsistently one column over.

**2.6 The panel-toggle button silently no-ops on narrow windows.** **FIXED** — the binding no longer fights the width guard, and the icon reflects the state.

> *Original finding:* (code)
Between the main-window minimum (600) and the inspector threshold (860), pressing the
"Show panel" toolbar button sets `ui.showPanel = true` but the binding's getter returns
`false` (width guard), so nothing happens — no panel, no explanation, a button that appears
broken. Same class of problem: the button's icon (`sidebar.trailing`) never changes state, and
its tooltip claims Hide/Show based on a value the view may not be honouring.

**2.7 Selecting a conversation steals focus from search.** **FIXED** — the composer only claims focus when nothing else has it.

> *Original finding:* (code)
`.task(id: store.selection)` re-focuses the composer 120 ms after every selection change —
including when the user is mid-word in the sidebar search field and clicks a result. Their next
keystrokes go into the message box.

**2.8 Streaming replies out-scroll the viewport; readers get yanked to the bottom.** **FIXED** — auto-scroll follows content growth, only while you are already at the end, with a Jump-to-latest button otherwise.

> *Original finding:* (code)
Auto-scroll fires only on message-*count* change. A reply that grows in place (`store.replace`)
never re-anchors, so the tail of a long streaming answer disappears below the fold. Inversely,
when the user has deliberately scrolled up to read history, any new message force-scrolls them
to the bottom. There is no "you're reading history / N new messages ↓" pill, which is the
standard resolution for both.

**2.9 A failed run offers no retry.** **FIXED** — the failure row carries Try again, wired to the last thing you actually asked for.

> *Original finding:* (code)
`MessageRow` renders `.failure` through `ErrorState` *without* passing the `retry` closure the
component was built with. Dead-end error: the user must re-type or re-copy their request.

**2.10 Messages have no actions and no context menus anywhere.** **FIXED** — copy/delete on bubbles, copy arguments and result on tool cards, copy command on approvals, reveal-in-Finder on screenshots, and roster/run-row menus.

> *Original finding:* (code)
No copy button, no right-click menu on bubbles, tool cards, screenshots, roster rows, or run
rows; no edit-and-resend, no delete message, no clear conversation, no "copy command" on the
approval card's mono block (selection-drag only). For a Mac app this absence is felt within
minutes of real use.

**2.11 No timestamps in the transcript.** **FIXED** — day separators, per-message times on hover, and tool durations.

> *Original finding:* (code)
`Message.timestamp` exists and is never rendered — no times on hover, no day separators. In a
product whose stated identity is "the record of the work", the record has no visible time axis.
`ToolActivity.startedAt/finishedAt` are likewise never surfaced (no durations), and
`routineID` ("happened on a schedule") has no rendering.

**2.12 Multi-line code from a bot is flattened into an unrunnable line.** **FIXED** — `ProseBlock` splits fenced code from prose; code keeps its newlines, scrolls sideways, and has a Copy button. 13 tests.

> *Original finding:* (live)
`TextBubble` parses with `.inlineOnlyPreservingWhitespace`; a fenced block arrives as
`bash mkdir -p ~/Desktop/… mv ~/Desktop/…` — language tag leaked into prose, newlines gone,
two commands fused. Screenshotted. The comment argues bots are told to write prose, but the
first thing the seeded bot does when asked about files is emit a fence (it did, in the
fixture modelled on real output). Anyone copying that line gets a broken command — in a shell
context this is not cosmetic.

**2.13 Stale "Running" is forever.** **FIXED** — see 1.4 — ADR 0013.

> *Original finding:* (code + live)
Kill or crash mid-run and relaunch: tool cards persist with status `running` (amber "Running"
pill, screenshotted) and the computer card with "Waiting for you". Nothing on launch sweeps
open activities whose run no longer exists. The transcript asserts work is happening that
is not.

**2.14 The Screen pane — the inspector's default — can never show anything.** **FIXED** — it shows the most recent frame the bot acted on, and says something true when there is none.

> *Original finding:* (code)
`ScreenPane` is a hardcoded placeholder ("No screen yet — appears when this bot uses a
computer") with no wiring to any frame source, while real screenshots go to the transcript.
Every launch opens the inspector on a promise the code cannot keep; on an empty roster it even
promises a screen for a bot that does not exist (screenshotted). Either it should show the
latest frame (as its own doc-comment describes) or it should not be the default pane.

**2.15 Three different things are called "Settings", two behind the same gear icon.** (code)
The conversation-header gear opens the inspector's *bot* pane titled "Settings"; the account
popover's "Settings…" and ⌘, open the *app* Settings window; the empty-conversation intro
("Give this bot a description in Settings") means the first one but reads as the second. A
user sent to "Settings" has a coin-flip chance of the wrong surface.

**2.16 Channels exist in the model and the sidebar, and nowhere else.** (code + live)
`createChannel`, `ChannelPolicy`, lead bots, the stacked-avatar row — all present; no UI can
create a channel, open one correctly, or edit its policy. Opening the fixture channel shows the
*first participant's* avatar and brain chips as if it were a 1:1 chat, `BotRunner.send` routes
to `participants.first` only, and the channel title/roster is unrepresented. The stacked
avatars are also clipped: the ZStack frame is `avatarRoster + md` (32 pt) but three offset
avatars need 40 pt, so the third is cut (screenshotted). One of the product's five named
objects is effectively decorative.

**2.17 Sheets ignore Escape.** **FIXED** — both carry `.cancelAction`.

> *Original finding:* (code)
Neither `LibrarySheet` ("Done") nor the screenshot zoom sheet ("Done") attaches
`.keyboardShortcut(.cancelAction)`, so ⎋ does not dismiss — a direct HIG violation on both.

**2.18 The approval card offers three of the model's four answers.** **FIXED** — four buttons; `deniedAlways` writes a never-rule.

> *Original finding:* (code)
`ApprovalRequest.Answer` includes `.deniedAlways` and the card renders a label for it — but no
button produces it. "Never allow this" (the counterpart to "Always allow") cannot be expressed,
so refusals must be repeated forever. (The research doc's four-resolution card was the stated
target.)

**2.19 First-run failure beats first-run guidance.** **FIXED** — the composer shows a preflight strip with an Add-a-key link when the answering brain has no key.

> *Original finding:* (code)
With no key saved, nothing stops composition: the user types, sends, waits, and gets a failure
bubble. The only advance warning is a 10 pt amber triangle in a chip. A preflight state on the
composer (or intro) saying "add a Gemini key first — Settings ⌘," would convert the first
minute from an error to a step. Related: the chip's warning is icon-only — `Chip` colours the
icon but always renders its *text* secondary, so the warning does not read as words.

**2.20 The activity stream and the Activity window do not know about each other.** **FIXED** — the stream links to the window, which has ⇧⌘0 and reloads when it comes forward.

> *Original finding:* (code)
The in-conversation "Activity" disclosure has no link to the full Activity window; the Activity
window has no path back to a conversation; it is reachable only via the account popover (or the
Window menu), has no keyboard shortcut, and does not refresh itself when a new run starts while
open (manual Reload only).

**2.21 Search: no shortcut, no clear affordance, no result context.** **FIXED** — ⌘F focuses it, there is a clear button, Escape clears, every message kind is searched, and a hit shows the line that matched.

> *Original finding:* (code)
⌘F does nothing (no `.searchable`, no focus command). There is no ✕-to-clear and Escape does
not empty the field. Matches on message *content* display only the unrelated last-message
preview, so a hit gives no indication of why it matched. Search also cannot find tool
summaries, notices, or failures — only `.text` bodies.

**2.22 Attachments are pasted paths.** **FIXED** — files can be dropped on the composer, with a drop target.

> *Original finding:* (code)
"Attach a file" appends raw absolute paths as lines of draft text — no chips, no removal
short of text-editing, no drag-and-drop *into* the composer at all, and no validation that the
bot can read them. Dragging a file onto the window does nothing. For a files-first agent app,
drag-and-drop is the expected primary path.

**2.23 ⌘N was repurposed and "New Window" died with it.** **FIXED** — ⌥⌘1, ⌥⌘2, ⇧⌘0 and ⌘F added to the menu bar.

> *Original finding:* (code)
`CommandGroup(replacing: .newItem)` removes the whole group, so there is no New Window command
(and no ⌘T-style alternative). Fine if single-window is a decision; currently it is a side
effect. Also missing entirely: ⌘F (search), ⌘1/2/3 (panes), ⌘⇧A (activity), ⌫ (delete bot),
⌘I (bot info) — the app has exactly one custom shortcut.

**2.24 `Store.load` decode failures silently discard unknown-to-it state.** **FIXED** — the file is kept under a new name and a sheet says where it is. Tested.

> *Original finding:* (code)
On any decode failure the whole document is moved aside and the app re-seeds as if new. The
user sees a fresh app with a stranger bot and no explanation that their data was set aside to
`state.json.corrupt-*` — recoverable on disk, invisible in product. A decode failure after an
app *update* (schema drift) would present as total data loss with a cheerful onboarding bot.

## 3. Visual & design-system violations (the system contradicting its own contract)

**3.1 Opaque fills on the material layer.** **FIXED** — the roster is a `List`, so selection and hover are the system's own material.

> *Original finding:* (code + live) Tokens declare: anything over the
sidebar/inspector material must use `DS.Tint` alphas, "every `Color.white.opacity` is a bug",
opaque surfaces flatten the material. The sidebar's selected row uses opaque
`DS.Surface.active` and hover uses opaque `DS.Surface.raisedHover` (both visible as flat grey
slabs against vibrancy in the screenshots); the Activity window's selected run row uses
`DS.Tint.t5` — the same state, different system, inconsistently.

**3.2 Tertiary ink (2.2:1) carries text people must read.** **FIXED** — 25 sites promoted to secondary; tertiary now appears only on decorative glyphs and the idle dot.

> *Original finding:* (code + live) The token's own
comment: "decorative and disabled only. Never a string the user must read." It is used for:
sidebar relative times, screenshot captions, approval *reasons*, activity-step timestamps and
details, connection detail lines, empty-state messages, "written by this bot", the account
popover's… — a dozen-plus real-content sites, all below WCAG minimums. The
missing-screenshot caption in the live shot is near-invisible.

**3.3 The approval colour rule is broken exactly as the token warns.** **FIXED** — the activity stream's approval row uses `awaitingApproval`, not `running`.

> *Original finding:* (code) Tokens:
"`running` and `awaitingApproval` must never share a colour." The live-stream row for an
approval is tinted `DS.Status.running.mark` (amber — running's exact colour); the approval
card and pill use `waiting` blue; the dedicated orange `awaitingApproval` mark is used only in
the settings floor list. Three surfaces, three colours, including the one forbidden collision.

**3.4 `design: .rounded` is banned by the type tokens and used by `BotAvatar`.** **FIXED** — removed.

> *Original finding:* (code)

**3.5 The status ramp is built and unused.** **FIXED** — `StatusPill` now uses the glyph, label and chip from `DS.Status`.

> *Original finding:* (code) `DS.Status` defines mark/label/chip/word
per state (Radix 9/11/3, all contrast-checked); `StatusPill` ignores all of it — grey chip,
secondary text, dot only. The carefully-authored "Needs you" vocabulary appears nowhere in the
product.

**3.6 Scroll indicators.** **FIXED** — the transcript no longer forces its content to viewport height, so it is only scrollable when there is something to scroll, and indicators follow the system setting.

> *Original finding:* (code + live) The transcript sets `.scrollIndicators(.hidden)` —
the comment beside it claims "appears only while scrolling", which is `.automatic`'s
behaviour, not `.hidden`'s. Users get no position affordance and the system-wide "Show scroll
bars: Always" preference is overridden. Meanwhile the sidebar's indicator *overlaps the row
content*, sitting on top of the timestamps (screenshotted) — rows carry no trailing inset for
it.

**3.7 The scrolled-header hairline is imperceptible.** (live) `Tint.t6` at 1 pt over `ground`:
in the rich screenshot the computer card visually collides with the header with no legible
separation. The mechanism (hairline appears on scroll) works; the value is too faint to do its
job.

**3.8 A reproducible unexplained dark strip renders at the conversation/inspector boundary.** **NOT FIXED — earlier claim withdrawn.** A re-verification pass measured this properly and the first diagnosis was wrong. Two different things were being conflated:
> - A *bright, full-height* scrollbar, visible in the empty state, caused by the transcript forcing its content to viewport height. That one is real and is fixed (see 3.6).
> - This faint band, which is still present. Measured: a smooth ~21 pt vertical gradient at the inspector's leading edge, peaking about 6% lighter than the surface, **identical at every row**, present when a bot is selected and absent when not. Ruled out by experiment: it is not the transcript's scroll indicator (hiding them changes nothing), not the inspector's (same), and not the desktop showing through translucency (the wallpaper behind it is flat). It is present in the pre-fix screenshots at the same relative position, so it is long-standing and was never affected by this work. Still unidentified.

> *Original finding:*
(live ×4) A ~10 pt wide, several-hundred-point tall rounded dark bar appears just left of the
inspector's leading edge in every fixture screenshot, roughly vertically centred, height
varying slightly. Likely the inspector's scroll view or divider drawing over the painted
`ground`; needs isolation. Whatever it is, it ships in every current screenshot.

**3.9 The empty-conversation intro is pinned to the bottom.** **FIXED** — same root cause; the intro is centred again.

> *Original finding:* (live) Because the transcript
bottom-anchors all content, the avatar+persona intro hugs the composer and the upper ~60% of
the pane is void (screenshotted twice). The intro was designed as a centred hero; the pinning
frame turns it into a footnote. Same effect makes one-message conversations look like they
fell to the floor of the window.

**3.10 "in 0s".** **FIXED** — times are clamped to the present and read "now" under 45 seconds.

> *Original finding:* (live ×3) Every freshly created bot's row shows "in 0s" — a *future* tense
for an event that just happened — because `RelativeDateTimeFormatter` receives a date
microseconds ahead of `Date()`. Clamp to "now". My future-dated fixture also stayed "in 1m"
without ever being flagged as clock skew, so a wrong system clock will happily render future
history.

**3.11 Unfilled icon buttons have no hover state.** **FIXED** — every variant responds to the cursor.

> *Original finding:* (code) `IconButton(filled: false)` — the
variant used for *every header control* (gear, panel toggle, plus, reload) — tracks `hovering`
and renders nothing with it: the hover circle only exists when `filled`. The interaction
layer's own promise ("a list whose rows do not respond to the cursor reads as a picture")
applies verbatim.

**3.12 The mascot's rest position reads as misalignment.** **FIXED** — the walk is centred in the composer it stands on.

> *Original finding:* (live) Between walks the mascot
stands at the extreme left of the composer column (its travel-0 position), visually an
un-centred orphan above the field's left corner. Its idle *placement*, not its animation,
is what reads as a layout bug in three of the five screenshots — and at 22 pt the six states
mostly read as "standing" vs "moving"; waiting-vs-working legibility at this size was never
verified against real users.

**3.13 Assorted single-surface defects.** (code, one line each)
- ApprovalCard buttons: three adjacent low-emphasis buttons; no default/primary, no
  keyboard activation, destructive "Deny" rendered like a filter chip.
- `ScreenshotCard` skeleton is a fixed 220 pt box "sized like the image" — it isn't; layout
  jumps on load for any other aspect.
- Zoomed screenshot sheet: no title, no filename, no Reveal in Finder / copy; "Done" only.
- `EmptyState` in the Activity window's detail pane uses icon `sidebar.left` for "select a
  run" — wrong metaphor (that icon is the roster toggle glyph).
- Settings "Saved gemini." confirms with the internal provider id, lowercase, not the display
  name.
- `Chip` caps height at `controlHeight` but its *menu* hit target is the visual ~20 pt pill —
  below the 28 pt `DS.Size.hit` floor the tokens mandate.
- Composer controls row reserves its 8 pt VStack gap even when no bot → dead space under the
  field in the empty state.
- The account row shows `NSFullUserName()` — the macOS account, implying an in-app identity
  that doesn't exist; its popover duplicates Settings/Quit reachable elsewhere, and "Activity"
  — a primary surface — is buried in it as the only entry point besides the Window menu.

## 4. Accessibility

**4.1 VoiceOver cannot operate the app.** **FIXED** — the two lists are `List`s; cards, rows and the transcript carry labels, traits and hints.

> *Original finding:* (code) Roster rows, run rows, step rows, tool cards
— all `onTapGesture` on plain views: not exposed as buttons, no labels, no selected state, no
actions. The two core lists and the transcript's interactive cards are silent.

**4.2 Icon-only buttons lack accessibility labels.** **FIXED** — `IconButton` takes an explicit label and falls back to its help text.

> *Original finding:* (code) `IconButton` sets `.help()`
(tooltip) but no `.accessibilityLabel`; the send button is announced, if at all, as
"arrow.up". Symbol-derived names are not reliable labels.

**4.3 Text does not scale.** (partial) Fonts are semantic (good — they track the system
scale), but glyph fonts are fixed 10/12 pt, every container (`bubbleMax`, `sheetHeight`,
`titlebar`, pill floors) is a fixed point value, and nothing was ever laid out at a larger
content size — a user on a larger text size gets clipped chips and overflowing fixed-height
sheets. Unverified visually; structurally certain to break.

**4.4 Reduce Motion has leaks.** **FIXED** — Spinner, Skeleton, PrimaryButton and PressableStyle all route through the gate.

> *Original finding:* (code) The `gated()` chokepoint is well built and most calls
route through it — but `Spinner` and `Skeleton` animate with raw `.animation(...repeatForever)`

**4.5 Colour-only signals.** **FIXED** — run rows carry an outcome word; the status pill carries a glyph and a word.

> *Original finding:* (code) The connection-status dot (healthy/degraded/error) has no
shape or word except in trailing text sometimes two lines away; run-list dots likewise. The
tokens' "never colour alone" rule is kept by `StatusPill` and broken by both dot-only sites.

**4.6 Contrast, again, structurally.** 2.2:1 tertiary on real text (3.2) and 1 pt `t6`
hairlines as the only structure means the app fails WCAG AA for text and non-text contrast in
routine places, in its only theme. Increase Contrast is partially honoured (semantic inks) and
ignored by every Radix-fixed surface and border.

## 5. Architecture-level UX hazards (wiring that will bite users)

**5.1 Two `UIState` instances exist.** (code) `BotHarnessApp` creates one and injects it;
`RootView` creates its *own* and re-injects it, shadowing the first for the whole tree. The
⌘N command's `ui.focusComposer()` mutates the orphaned app-level instance. Harmless today only
because `focusRequests` has **zero observers** (grep) — the counter, its comment, and its two
call sites are dead code from a previous fix, and the machinery will mislead the next person
who wires a caller to the wrong instance.

**5.2 Two `CapabilityRegistry` instances.** (code) `BotRunner` owns one (used by runs);
`ConnectionsModel` builds a second for the Library sheet. The sheet's "Connections" status is
therefore a parallel probe, not the state bots actually run with — they can disagree, and
Refresh in the sheet fixes nothing the runner sees.

**5.3 The Settings opener is a private selector.** (code)
`NSApp.sendAction(Selector(("showSettingsWindow:")))` in two places — undocumented AppKit,
already renamed once (`showPreferencesWindow:` → `showSettingsWindow:`); a future macOS can
silently turn both "Set up keys…" and the account popover's Settings into no-ops.
`SettingsLink` is the supported API.

**5.4 Whole-document rewrite on every message.** (code, acknowledged in-file) Every token
batch rewrites all conversations pretty-printed; with the file's own stated revisit threshold
(10k messages / 50 MB) the debounce means multi-MB writes several times a second during a
chatty run. No migration/versioning beyond `version: 1` either — see 2.24 for what a failed
decode presents as.

**5.5 Sidebar search is O(everything) per keystroke on the main thread.** (code) Full linear
scan of every message body of every conversation per character typed.

**5.6 `ScreenshotCard` re-decodes on every scroll pass.** (code) `task(id:)` reloads from disk
each time lazy recycling re-materialises the row; no cache. Long screenshot-heavy transcripts
will hitch on scroll.

**5.7 `RelativeDateTimeFormatter` allocated per row per render.** (code) Known-expensive
formatter; the roster re-renders on every keystroke of search. Also: the timestamps never
update while the app sits open (no timer), so "2m ago" stays "2m ago" for an hour — the live
`.relative` style used in the Activity window does update, making the two lists disagree in
behaviour.

## Addendum, 2026-08-31 — responsiveness, found by actually resizing the window

**The original audit did not test this.** Every screenshot in it was taken at the default
1280×820. Items 2.5 and 2.6 discussed narrow windows from reading the code, but no window was
ever resized, and the two worst layout defects in the app were only visible when one was. They
were found by driving the real window through ten sizes from 1800 down to 600 points with the
Accessibility API and measuring the result.

**R1 — the transcript lost its right-hand side below roughly 900 points.** **FIXED.**
`ReadingColumn` measured its own frame in a `.background` and fed that width back into
`.frame(width:)`. That is circular: on the first layout pass there is nothing to measure, so
the column sized to its content's *ideal* width, that ideal propagated upward as the pane's
minimum, and the pane was laid out wider than the window with the overflow simply cropped.
Status pills, the Try-again button, the send button and the end of every sentence were gone —
not truncated with an ellipsis, cropped. Replaced with a max-width frame inside an HStack with
a zero-minimum Spacer, which states "up to this wide, less if that is all there is" directly
and measures nothing.

**R2 — a closed inspector still reserved its width.** **FIXED.** `.inspector()` was attached
unconditionally, and it reserves `inspectorMin` even while `isPresented` is false. The detail
pane therefore demanded `conversationMin + inspectorMin` = 680 points at every size, so any
window narrower than that plus the roster cropped the difference. The inspector is now attached
only when the window can hold it; below that threshold it does not exist rather than existing
invisibly.

**R3 — the roster-collapse threshold was computed from the wrong number.** **FIXED.** It used
`rosterMin` (180), but the split view keeps the sidebar near `rosterIdeal` (240) rather than
compressing it, so between about 600 and 660 points the roster stayed wide and pushed the
transcript below its own minimum. The threshold now uses the width the roster actually takes.

**R4 — the panel toggle was still offered when no panel could fit.** **FIXED.** The earlier fix
keyed off `panelClosedByWindow`, which only records who closed it last; a window that launches
too narrow has closed nothing, so the button was present and inert. It now keys off whether the
inspector can fit at all, and is hidden when it cannot.

Verified after the fixes at 1800×1000, 1400×860, 1200×572, 1000×660, 860×600, 820×580,
760×560, 700×540, 660×540 and 600×572: no clipping at any size, the roster collapses and
returns via the toolbar button, and the code block scrolls horizontally rather than forcing the
column wider.
