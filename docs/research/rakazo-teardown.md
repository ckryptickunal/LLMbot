> [elie222/rakazo](https://github.com/elie222/rakazo) — "Open-source Grok Bot alternative.
> Choose your own model and sandbox." Apache-2.0, ~1.5k stars, TypeScript monorepo.

## The agent runtime — loop, tool definition and dispatch, streaming, context assembly

### How it works

The agent loop is not in packages/core/src — that package is pure UI and domain helpers. The loop is one 2,260-line method, continueRun(runId, workerId), inside createRunExecutor in packages/adapters/src/executor.ts; the model-facing half is PiAgentRuntime.run in packages/adapters/src/pi-runtime.ts, which wraps a third-party Agent class from pi-agent-core. A turn is: lease the run row with a monotonically increasing fence token (nextFence in packages/core/src/run-state.ts), create an Attempt row, start a 60-second heartbeat renewing the run lease and computer lease that aborts the turn if either renewal fails, load bot/thread/messages/task/skills in one Promise.all, assemble the prompt, then iterate over deps.runtime.run(). The runtime yields a flat union AgentRuntimeEvent (packages/adapter-kit/src/types.ts) of text, progress, tool, ask, takeover, subagent, usage, done, produced by a hand-rolled push queue (createQueue at the bottom of pi-runtime.ts) that bridges Pi's callback subscribe into an async iterable — structurally the same as our AsyncStream. Tools are declared as data only: ConnectorTool is name, description, inputSchema, readOnly, route, with no handler attached (packages/adapter-kit/src/types.ts); the 33 builtins live in packages/adapters/src/builtin-tools.ts and execution is a single callback request.executeTool(name, args, executionId, route) landing in applyTool, a flat if-name-equals chain. Schemas are declared twice: JSON Schema in builtin-tools.ts, and TypeBox schemas plus per-tool argument coercion again in parametersFor and prepareArguments in pi-runtime.ts. Tool results reach the model as either a plain JSON value that gets stringified and clipped to 12,000 characters (summarizeToolResult), or a structured AgentToolExecutionResult with text and image parts; read_file refuses anything over MAX_MODEL_FILE_BYTES (250,000) rather than truncating. Context assembly is two-tier: a rolling window of thread messages rendered to plain text by blocksToAgentHistoryText, plus a model-written summary advanced by a compaction cursor in packages/adapters/src/history-compaction.ts. Crash recovery rests on an external-effect journal (packages/adapters/src/approval-effect.ts) keyed by a sha256 of canonically-serialized arguments (approvalEffectKey in packages/core/src/approval-effect-key.ts), so a re-run replays approved calls in order and refuses to repeat one whose outcome is unknown. There is no planner, no task graph, and no completion verifier — a turn ends when the model stops calling tools, or when the identical-call loop guard, the tool-call budget, or lease loss stops it.

### Patterns worth taking

#### Write-ahead effect journal with an explicit uncertain state  ·  high value, medium effort

**What.** Before any non-read-only tool runs, a row is written with status intended, keyed by sha256 of the canonically-serialized arguments plus run id and tool name (approvalEffectKey, packages/core/src/approval-effect-key.ts; recordEffect at executor.ts:3007). It moves intended to executing to completed. On a later attempt, resolveDuplicateEffectGate (approval-effect.ts) maps the stored status to an action: completed returns the stored result without re-running, denied returns a denial, and executing means the process died mid-side-effect, so settleUncertainEffect flips it to uncertain and hands the model a tool result reading: the earlier execution was interrupted, its outcome is unknown, it was not replayed to avoid a duplicate side effect, verify the destination before proposing another action.

**Why it beats the obvious alternative.** Our hash-chained trace records what happened; it does not tell a resumed run what it must not do again. The valuable half is not the journal, it is that 'unknown outcome' is a first-class value returned to the model as data rather than an exception. The model then re-observes instead of blindly re-sending an email or re-clicking Buy. The canonical-JSON hash also means an approval granted for one exact payload cannot be spent on a payload the model reconstructs slightly differently after the resume.

**For us, in Swift.** An append-only effects.jsonl next to the trace, plus an in-memory dictionary keyed by effect id, both owned by the same actor that owns the tool dispatch. Effect id is SHA256 (CryptoKit) over a canonical JSON encoding with sorted keys (JSONEncoder.OutputFormatting.sortedKeys gets you most of the way; reject non-finite numbers as they do). Write the intended record and fsync before calling the executor, write the completed record with the result after. On launch, replay the journal: any record still in executing becomes uncertain, and the ToolResult surfaced to the brain on the next turn is a plain string, not a thrown error. Mark read-only tools exempt via a flag on ToolDescriptor, the same way READ_ONLY_AGENT_TOOLS works at executor.ts:209.

#### Two-mechanism screenshot economy  ·  high value, small effort

**What.** frameId is sha256 of the raw screenshot bytes (computer-support.ts:34). observationToolResult (computer-tools.ts:60) compares it to the previous frame and, when identical, returns text only with the marker (screen unchanged) and attaches no image at all. Separately, pruneComputerScreenshotContext (pi-runtime.ts:795) runs as Pi's transformContext before every model call and strips the image parts from every screenshot tool result except the most recent two, keeping the surrounding text.

**Why it beats the obvious alternative.** These are independent and both matter. The hash check kills the common wait-and-look-again loop that otherwise costs a full image per poll. The keep-last-two prune bounds context growth over a long GUI session without rewriting history, and it is applied at call time rather than mutating the stored transcript, so the record stays complete. We capture with ScreenCaptureKit on every observe and would otherwise carry every frame forward.

**For us, in Swift.** In the macOS executor, hash the captured CVPixelBuffer or PNG data with SHA256 and carry lastFrameHash on the run actor; if unchanged, return a text-only ToolResult saying so. For the prune, keep tool results in the context array with an associated imageData field and a marker that this result was a screen capture, and build the provider payload through a function that drops imageData for all but the last two such results. Do the same for the accessibility tree dump, which has the same shape.

#### Streaming secret redactor that survives chunk boundaries  ·  high value, small effort

**What.** createStreamingRedactor (packages/core/src/events.ts:326) sorts known secret values longest-first, buffers incoming deltas, and only emits characters up to buffer.length - maxSecretLength + 1, holding back the tail so a secret split across two deltas is still matched. finish() drains the remainder. The executor threads every streamed text delta through it (progressRedactor.push) and calls finish() before the final flush, and separately refuses to persist a completed message if containsSecret still matches.

**Why it beats the obvious alternative.** Naive per-chunk redaction leaks any secret that straddles a token boundary, which is exactly what happens when a model echoes an API key. The whole mechanism is about thirty lines and is trivially unit-testable. We stream brain output to the UI and to the trace; both are places a leaked key becomes durable.

**For us, in Swift.** A small struct with a String buffer and a sorted [String] of secrets, mutating func push(_ chunk: String) -> String and mutating func finish() -> String. Feed it every delta before it reaches the conversation view or the trace writer. Populate the secret list from the Keychain values already loaded for the run, the way runSecrets is assembled at executor.ts:695.

#### Identical-call loop guard that ends the run as a completed turn  ·  high value, small effort

**What.** trackToolCallStreak (events.ts:239) keys on name plus JSON.stringify(args) and counts consecutive repeats; advanceToolCallLoopGuard (packages/adapters/src/tool-loop.ts) trips at 6. When it trips, the executor at executor.ts:2540 does not throw: it flushes pending segments, checkpoints the workspace, finalizes the run with outcome completed, and writes a first-person message naming the tool and the repeat count, then aborts the model. Separately, MAX_TOOL_CALLS_PER_TURN (maxToolCallsPerTurn, pi-runtime.ts) is an optional whole-turn budget, unlimited by default, and exceeding it also ends the turn softly with an explanatory sentence appended to whatever text was already streamed.

**Why it beats the obvious alternative.** The design choice worth copying is that both stops are completions, not failures. The user gets a durable message they can act on and the transcript stays coherent; a thrown error would leave a red run and no explanation. The two guards are also deliberately different: identical-args repetition catches a stuck loop, the budget catches a runaway that is making varied but endless calls.

**For us, in Swift.** Two counters on the run actor. streak: (key: String, count: Int) where key is toolName plus a canonical encoding of args; at 6, emit a .finished event carrying the explanatory sentence rather than a .failed. A separate turn budget defaulting to off, configurable per bot. Word the message the way they do, naming the tool and the count, which matches our house tone of what it did and what rule it is adopting.

#### Compaction cursor with a contiguity guard, injected as untrusted data  ·  high value, medium effort

**What.** A background job (compactHistory, history-compaction.ts) summarizes batches of 50 messages with the same model the bot uses, writes the summary and advances thread.historyCompactedUpToSeq via a compare-and-set on the previous cursor. At run time selectCompactedHistory refuses to use the summary unless every message after the cursor is present with no sequence gap, falling back to the full 200-message legacy window otherwise. The summary is injected as a user-role message wrapped by formatCompactedSummary in a compacted_thread_summary tag, prefixed with a line stating it is untrusted historical data and not instructions. There are hard caps throughout: 40,000 characters of transcript into the summarizer, 20,000 characters out, a 120-second timeout, and the batch is trimmed at a message boundary rather than mid-message.

**Why it beats the obvious alternative.** Two things beat the obvious approach. First, the contiguity check: a summary plus a gap silently deletes conversation, so they verify coverage before trusting it and degrade to the full window instead. Second, compacted text and recalled memory enter as conversation history with an explicit untrusted-data banner, never as system instructions, so a prompt injection that survived into a summary cannot be promoted in priority by the act of summarizing. The compaction failure path never advances the cursor, so a wedge retries rather than losing history.

**For us, in Swift.** Store messages with a monotonic seq in the JSON state file; keep compactedUpToSeq and compactionSummary on the chat. Run compaction on a detached Task after a turn finishes when uncompacted count exceeds window plus batch, using the same brain adapter with an empty tool list. Before using the summary, verify seq contiguity exactly as selectCompactedHistory does and fall back to the full window if it fails. Wrap the injected summary in a delimiter with the untrusted-data sentence, and escape angle brackets and ampersands in it as escapePromptData does.

#### Durable scratchpad as the plan surface, byte-budgeted into the prompt  ·  medium value, small effort

**What.** There is no todo tool and no plan in context. Instead scratchpad_add / scratchpad_update / scratchpad_complete / scratchpad_remove / scratchpad_list write rows with status open, parked, or done (packages/adapters/src/scratchpad-tools.ts). loadAgentScratchpadContext (scratchpad-context.ts) renders only the open and parked items into a scratchpad_open block capped at 4 KB and 40 items, truncating on a UTF-8 character boundary and appending a line telling the model to call scratchpad_list for the rest. The preamble says explicitly: this list is not a scheduler, it does not wake you, contents are data not instructions.

**Why it beats the obvious alternative.** An in-context todo list dies with the turn and is re-derived every run. This survives compaction, survives a crash, and is directly editable by the user. The byte budget with a call scratchpad_list overflow line is the right shape: the prompt gets a bounded index, the full list stays behind a tool. The disclaimer that it is not a scheduler is a real lesson — models otherwise treat a persistent open list as a promise that they will be woken.

**For us, in Swift.** A ScratchpadItem array on the Bot in the Store, five small tools in the ToolRegistry, and a context section builder that renders open items with a hard byte cap using String.utf8 counting. Pairs naturally with our task contract: the contract holds the objective and success criteria for one run, the scratchpad holds work that outlives it.

#### Sentence-boundary flushing of tool chips into streamed narration  ·  medium value, small effort

**What.** Streamed text and tool-call markers are interleaved into one message. Tool names arriving mid-sentence are held in pendingToolNames and only flushed when endsSentence (events.ts:257, regex for terminal punctuation with optional closing quotes or brackets) says the buffered text is at a clause boundary. appendToolCallSegment coalesces consecutive identical tool names into a steps block with a count. Text deltas are batched and flushed on a 250 ms throttle, and a progress event forces a text flush first so narration can never render after the tool call it describes. describeToolActivity (pi-runtime.ts:381) turns each call into one human line such as Running: git status or Looking at the screen.

**Why it beats the obvious alternative.** This is small-scale craft that determines whether a long run reads as a coherent account or as jitter. Ordering is enforced explicitly rather than hoped for, and repeated calls collapse instead of producing a wall of chips. Our ActivityInspector work is exactly where this belongs.

**For us, in Swift.** A reducer over [MessageBlock] mirroring reduceLiveMessageBlocks: a pending tool-name array, an endsSentence check, and coalescing of adjacent tool steps into one block with a count. Throttle deltas with a timestamp check in the run actor rather than a Timer, and always drain buffered text before appending a tool block.

#### Same-process subagents with a shared budget and delegation tools stripped  ·  medium value, medium effort

**What.** run_subagent (executeSubagent, pi-runtime.ts:596) builds a second Agent in the same process, sharing the parent's model, api key, abort signal, and tool-call budget object. Its tool list is the parent's minus DELEGATION_TOOL_NAMES, so it cannot spawn further; depth greater than 0 refuses outright, and a gate caps concurrency at MAX_PARALLEL_SUBAGENTS = 4. It streams progress up as subagent events every 80 ms (last 800 characters), and returns a single string clipped to 12,000 characters. The parent's system prompt spends three lines distinguishing a subagent from a bot: a subagent is a short helper inside this turn with no thread and no listing, a bot is lasting and appears in the user's list.

**Why it beats the obvious alternative.** Delegation here is one tool, not an orchestration framework: no queue, no plan, no result schema. The shared abort signal and shared budget mean a stuck child cannot outlive or outspend the parent, which is the failure mode a naive implementation hits. Flat depth-1 only is a deliberate simplification worth copying rather than improving on.

**For us, in Swift.** A run_subagent tool that constructs a second instance of our loop actor with the same brain adapter, the same permission evaluator, a filtered tool set, depth 1 maximum, and the parent's Task cancellation propagated. Share one mutable budget (an actor-isolated counter). Surface progress as a distinct event case so the conversation view can render a collapsible child block. Cap concurrency with a small semaphore; their gate is fifteen lines.

#### Tool surface shaped by the model's actual declared capabilities  ·  medium value, small effort

**What.** modelAcceptsImageInput (packages/adapters/src/model-vision.ts) checks the resolved model's declared inputs, and filterImageReturningComputerTools removes computer_observe, computer_act, open_path and launch_app from the exposed list when the model cannot see. If such a tool is somehow called anyway, applyTool returns the string MODEL_CANNOT_SEE_MESSAGE rather than executing. The system prompt is also branched three ways at executor.ts:1004 so the model is told a different story about its computer in each case, and selectMemoryTools drops the semantic-memory tools when no provider is configured. A comment records a real bug here: the vision check originally re-derived the model separately from the row written to the run, so a vision-capable default was misgated as scripted and lost its screenshot tools.

**Why it beats the obvious alternative.** Filtering plus a guard at execution, not one or the other. And the branched instruction text matters as much as the filter: a model told it has a computer but given no way to look at it will hallucinate observations. We already route capabilities; the gap is that our capability decision and our prompt text are not derived from the same resolved model value, which is precisely the bug their comment documents.

**For us, in Swift.** Derive one resolved model value at the top of the run and pass it to both the tool filter and the prompt builder; never recompute. Add an acceptsImages flag to the brain adapter's model description. Keep the belt-and-braces error string in the tool dispatch for anything filtered out.

### Not applicable to us

- Lease fencing plus Postgres advisory-lock leader election plus a scanning job reconciler (packages/adapters/src/job-reconciler.ts, createPostgresReconciliationLeadership). This exists to stop two workers in a fleet running the same run; a single-user local app has one process. The narrow piece that does survive is the run status transition table in packages/core/src/run-state.ts, which is a plain dictionary of legal transitions plus assertTransition and is worth copying as-is for our run lifecycle.
- Every compare-and-set implemented as prisma.updateMany with a where clause on the expected prior state, checking count === 1. That is the correct pattern against a shared database and pure ceremony inside a Swift actor, where the actor already serializes the read-modify-write. Copy the state machine, not the concurrency control.
- Graphile Worker background jobs for compaction, routine wakeups, and computer sleep. On macOS these are a detached Task, a Timer, or launchd for anything that must survive app exit — no queue server.
- The semantic memory provider (supermemory-client.ts, supermemory-memory-provider.ts) with recall-by-query at run start and purge-by-generation on thread clear. It is a paid network dependency and violates our zero-dependency and local-first constraints. The local half of the same feature, the compaction cursor and summary, is fully applicable and is listed above.
- OAuth-per-workspace model credential resolution (resolveModelKey, findModelCredential, withModelCredentialLock, pi-oauth.ts, mcp-oauth.ts). Multi-tenant credential scoping that collapses to one Keychain item for us.
- spawn_bot / archive_bot / message_bot with a six-hop chain limit (bot-messages.ts) as a general mechanism. The hop limit and the untrusted-peer-message wrapper in buildBotMessageWakePrompt are genuinely good, but async bot-to-bot messaging needs a wake-and-queue substrate we do not have and should not build for a single-user app. Worth revisiting only if our bot roster ever gains background runs.
- The 12,000-character JSON stringify-and-clip in summarizeToolResult. It is the weakest part of their result handling: it truncates mid-token with no structure preservation and no indication to the model of how much was dropped. Our tool layer should return typed, deliberately-shaped results instead. Copy the idea of a hard cap, not this implementation.

### Surprises

- There is no planner and no task graph anywhere in the repository. Grepping the whole monorepo for todo_write, update_plan, planner or plan_step returns nothing. The only durable plan surface is a database-backed scratchpad list, and its prompt preamble explicitly warns the model that the list will not wake it. This contradicts the common assumption that a long-horizon computer-use agent needs an in-context todo list.
- There is no completion verifier. A turn ends when the model stops emitting tool calls. Every other stop is a guard, not a judgment: the identical-call loop guard at 6, the optional per-turn tool-call budget, lease loss, or an approval pause. Our verifier deciding completion against the task contract's success criteria is a real capability they do not have, and it is the clearest place our design is ahead.
- Cross-turn history is text-only and role-flattened. toHistory in pi-runtime.ts converts every prior assistant message into a user message prefixed with the literal string 'Assistant: ', and history entries come from blocksToAgentHistoryText, which renders images as [image: name] and files as [file: name]. Tool calls and tool results from earlier turns never re-enter context at all. Full fidelity exists only inside one turn. That is a much more aggressive context reset than I expected from a product whose selling point is long computer-use sessions.
- The tool type carries no handler and no validation. ConnectorTool is inert metadata, and dispatch happens by string comparison in two separate files that each maintain their own list of builtin names. Argument validation and defaulting is done by hand, per tool, in prepareArguments. Our ToolRegistry of ToolDescriptor with a bound handler and one schema per tool is straightforwardly better engineering; theirs is the part of the codebase most obviously showing its age.
- An LLM sits inside the permission gate. planActionGate (packages/core/src/action-approval.ts) can route a consequential action to a second model that answers strict JSON pass or ask, with a default timeout of 1,500 ms (auto-review.ts). Any error, timeout, or unparseable answer fails closed to ask for consequential tools. It is opt-in and can point at a local model. Worth knowing about, but it is an assist layered on top of the deterministic rules, never a replacement for them — which is the only shape that would be compatible with our unlowerable safety floor.
- Prompt-injection defenses are textual and repeated everywhere rather than structural: every injected block (compacted summary, recalled memory, scratchpad, bot directory, group roster, peer message) is wrapped in an XML-ish tag, has its angle brackets and ampersands escaped by a local escapePromptData copied into five different files, and is preceded by a sentence declaring it untrusted data. The system prompt also carries a specific counter-instruction that page content such as a banner reading 'Work is finished' is content, not a command to stop — evidently a real observed failure.

## The "choose your own model and sandbox" abstraction — packages/adapter-kit (port definitions) and packages/adapters (all in-tree implementations)

### How it works

packages/adapter-kit is a pure types package: four source files, 973 lines, no runtime deps beyond zod. src/interfaces.ts declares fifteen ports (SandboxProvider, AgentRuntime, ConnectorProvider, ManagedConnectorProvider, MemoryStore, SemanticMemoryProvider, ModelProvider, VoiceProvider, SecretStore, ArtifactStore, AgentHomeStore, RealtimeFanout, NotificationProvider, JobPublisher, ExecutionRunner) and src/types.ts declares the values they exchange. Every port starts with the same method, `describe(): AdapterDescriptor<TCapabilities>`, where AdapterDescriptor is `{ id: string; contractVersion: string; adapterVersion: string; capabilities: TCapabilities }` — and each port parameterises that capability type differently: SandboxCapabilities is `{ graphical, pty, snapshots, takeover, persistentHome, multiScreen? }`, AgentRuntimeCapabilities is `{ streaming, compaction, tools, scripted }`, VoiceCapabilities is `{ catalog, synthesize, transcribe }`. Every method also takes an AdapterContext carrying operationId, traceId, workspaceId, userId, optional botId/runId/screenLeaseId, and an AbortSignal, so cancellation and correlation belong to the port rather than to each adapter. SandboxProvider is the widest port at twenty methods, and its important shape is that provision() and prepare() are split: the doc comments say provision should "Allocate or reconnect the computer, returning its reference before fallible setup" and prepare should "Perform idempotent provider setup after the lifecycle has captured the reference", so a crash during setup cannot orphan a remote VM whose id was never written down. Bulk data crosses the port as AsyncIterable<PortableFile> (exportWorkspace/importWorkspace), which is what makes migrating a bot between sandbox backends possible at all. Selection is not dynamic: packages/adapters/src/sandbox-factory.ts is a plain switch over a string, mapping "none" | "docker" | "e2b" | "daytona" | "box" | "e2b-emulator" | "daytona-emulator" | "box-emulator" | "desktop" | "fake" to a constructor, with an unknown value throwing an error that lists the legal ones. Before that switch runs, sandbox-provider-env.ts resolveSandboxProvider() rewrites the requested kind to "none" when its credential is absent, with the comment "Empty or remote provider without a key becomes none so services can boot for signup". NoneSandboxProvider then implements the whole twenty-method port by throwing one fixed sentence that names the environment variables that would fix it. Nine SandboxProvider implementations ship (box, daytona, desktop, docker, e2b, fake, none, host-aware, plus three emulators subclassing FakeSandboxProvider); two AgentRuntime implementations (PiAgentRuntime, ScriptedAgentRuntime); four VoiceProvider; one SemanticMemoryProvider (Supermemory). The ModelProvider interface has zero implementations anywhere in the repo — the model side is not their code at all. packages/adapters/src/pi-models.ts calls builtinModels() from the third-party @earendil-works/pi-ai package and walks provider.getModels(), and Rakazo's own contribution is two synthetic providers registered into that catalog: pi-local-provider.ts (Ollama/LM Studio, keyless, models listed from an env var) and pi-openai-compatible-provider.ts (a placeholder catalog entry "custom" that the user fills in with a base URL and model id). Feature detection on the model side is a single field lookup: model-vision.ts modelAcceptsImageInput() checks whether the catalog entry's `input` array includes "image", treating unknown models as text-only. The two capability axes then intersect in executor.ts around line 934: `graphical = computer.kind !== "desktop" && deps.sandbox.describe().capabilities.graphical`, `acceptsImages = ...`, `graphicalToolsAllowed = graphical && acceptsImages`, and that boolean both filters the tool list (filterImageReturningComputerTools drops computer_observe, computer_act, open_path, launch_app) and selects one of three different paragraphs of system prompt describing what the bot can and cannot do.

### Patterns worth taking

#### Capability descriptor that gates the tool list AND rewrites the prompt  ·  high value, small effort

**What.** Each provider returns describe() with a small struct of booleans. The agent loop intersects capabilities from two different sources — the sandbox's capabilities.graphical and the selected model's declared image-input support — into one flag, then uses that flag twice: to filter the tools handed to the model, and to choose which of three system-prompt paragraphs is inserted. In executor.ts the three branches read roughly: full desktop instructions; 'You have a persistent computer filesystem and shell. This bot's model cannot see; pick a vision-capable model. Desktop observe and act tools are unavailable until a vision-capable model is selected.'; and a third for backends with no graphical control at all.

**Why it beats the obvious alternative.** Filtering the tool list alone produces a model that keeps proposing screenshots and then improvises when the tool is missing. Telling the model what it lost, and why, turns a silent capability hole into an explainable one — and the same boolean drives both, so they cannot drift. It is also the cheapest place to surface a user-fixable misconfiguration ('pick a vision-capable model') without adding UI.

**For us, in Swift.** Give each executor and brain adapter a `capabilities` property on its protocol (e.g. `struct ExecutorCapabilities { let screenCapture: Bool; let accessibilityTree: Bool; let syntheticInput: Bool }`, `struct BrainCapabilities { let acceptsImages: Bool; let toolCalling: Bool; let thinkingLevels: [ThinkingLevel] }`). In the context-assembly step, compute the intersection once into a small `RunCapabilities` value, use it to filter the tool registry before it becomes the tool schema, and use the same value in a `switch` that appends one of N prepared prompt fragments. This lands naturally where Bot-Harness already has a capability router.

#### Null-object provider plus boot-time downgrade instead of a crash  ·  high value, small effort

**What.** NoneSandboxProvider implements the entire twenty-method SandboxProvider port; every method calls a private fail() that throws one message naming the exact env vars that would fix it, and describe() honestly reports every capability false. resolveSandboxProvider() silently rewrites a configured-but-uncredentialed provider to 'none' before the factory ever runs, and even downgrades docker in production when the supervisor token is missing, so the app boots into a usable-but-degraded state instead of exiting.

**Why it beats the obvious alternative.** The obvious alternative is optionality (`sandbox: SandboxProvider?`) or a fatal error at startup. Optionality forces nil-checks at every call site; a fatal error means a missing key bricks the whole app. The null object keeps every call site unconditional, keeps the failure message at the exact moment of use rather than at launch, and lets describe() feed the same capability-gating machinery so the prompt already explains the degradation before anything throws.

**For us, in Swift.** Write a `DeniedExecutor: Executor` whose every method throws a `ToolError.unavailable(reason:)` carrying a one-sentence user-fixable message, and whose capabilities are all false. Select it at composition time when the relevant TCC grant is missing (Screen Recording or Accessibility not granted, no API key in the Keychain). For Bot-Harness this maps almost exactly: a denied Screen Recording grant should produce a shell-and-files-only executor with a message that names the System Settings pane, not a crash and not an optional.

#### Provider-tagged handles: route per object, not per current setting  ·  high value, medium effort

**What.** ComputerRef carries `kind: SandboxKind` and `providerRef: string` alongside its id. HostAwareSandbox holds two providers (isolated and host) and its private `route(computer)` picks one by reading `computer.kind`, so an existing machine always goes back to the provider that made it even after the user flips the setting. Only provision() consults the current setting, and when the kind changed it deliberately drops the stale providerRef before handing the request over. computer-lifecycle.ts then compares the returned ref against the stored row and, when `ref.fresh === true` or providerRef or kind differ, calls restoreComputerWorkspace() to replay the exported PortableFile stream into the new machine.

**Why it beats the obvious alternative.** The naive design routes every call through whatever provider the config currently names, which silently hands a Docker container id to the desktop provider the moment the user changes a preference. Tagging the handle makes the mismatch impossible to express, and the fresh/providerRef comparison turns a backend swap into an explicit, testable data migration rather than silent data loss.

**For us, in Swift.** Make the handle an enum-tagged struct rather than a bare identifier: `struct ComputerRef { let id: String; let kind: SandboxKind; let providerRef: String; let fresh: Bool }`, persisted in the Store's JSON alongside the bot. Have a router type conform to the same Executor protocol and dispatch on `ref.kind`. When provisioning returns a ref whose kind or providerRef differs from the stored one, run the export/import migration. Bot-Harness will hit this the first time it has both a local-shell executor and, say, a container or remote one.

#### One shared negative-contract suite run against every provider, with Proxy fault injection  ·  high value, medium effort

**What.** packages/adapters/src/sandbox-faults.test.ts uses describe.each over five providers (fake, three emulators, desktop) and asserts the same five behaviours for each: path traversal is rejected through all four workspace entry points (listFiles, readFile, writeFile, importWorkspace) with both forward and backslash separators; oversized and missing reads fail without returning partial data; an over-limit action batch is rejected before any action is applied and observation is unchanged; stop() is idempotent, a re-provision returns the same providerRef with fresh:false and preserved file contents, destroy() is idempotent, and the next provision returns fresh:true. The fifth uses a JS Proxy (faultOnce) that makes provision, prepare, importWorkspace and exportWorkspace each fail exactly once, then asserts the retry succeeds. A separate test runs the full source-to-target matrix of providers, writing a binary file with the executable bit and asserting bytes and metadata survive every pairing.

**Why it beats the obvious alternative.** Positive per-adapter tests let each adapter define its own idea of correct. A shared negative suite makes 'refuses to escape the workspace', 'idempotent teardown' and 'retryable after a mid-operation failure' properties of the port itself, so adding a provider means proving those properties rather than being trusted. The Proxy trick tests the crash-recovery path without needing a real crash, which is otherwise almost untestable. And the cross-product transfer test is what actually makes the export/import contract load-bearing rather than aspirational.

**For us, in Swift.** This is the highest-leverage import for Bot-Harness given it already has a 13-task eval suite: add a second, different axis of testing. Write one XCTest function taking a factory closure, and a parameterised runner over every executor implementation (real macOS, a fake, a denied one). Assert the safety-floor properties: containment refusal, idempotent teardown, no partial output on oversized reads, batch limits applied before any effect. Swift has no Proxy, so express fault injection as a decorator conforming to the same protocol with a set of method names to fail once. This suite is where the unlowerable safety floor stops being a claim about one code path and becomes a property of every executor.

#### Streaming redactor with an overlap buffer  ·  high value, small effort

**What.** createStreamingRedactor(secrets) in packages/core/src/events.ts sorts the known secret values longest-first, then on each push(chunk) only emits up to `buffer.length - maxSecretLength + 1` characters, holding the tail back until finish(). A secret split across two stream chunks is therefore still matched. The executor collects secrets into a runSecrets array as it decrypts each credential (including every field of an OAuth blob and any base URL), builds one redactor per run, and pipes all streamed progress text through it before appending to the event log.

**Why it beats the obvious alternative.** The obvious implementation redacts each chunk independently and leaks any key that happens to straddle a chunk boundary — which is exactly what streaming token output does. It also collects the secret values at the moment of decryption rather than trying to pattern-match key formats afterwards, so it catches base URLs and refresh tokens that no regex would recognise. (Their SecretStore.redact() regex for sk- and JWT shapes exists too, but only as a coarse second net.)

**For us, in Swift.** A small struct with `mutating func push(_ chunk: String) -> String` and `mutating func finish() -> String`, holding the sorted secret list and a residual buffer. Populate it at the start of each run from whatever the Keychain hands back for that run's brain adapter and MCP servers. Bot-Harness needs this specifically because the trace is append-only and hash-chained: a leaked key in the trace cannot be edited out afterwards without breaking the chain, so redaction has to happen on the way in.

#### Two-tier error classification with an explicit veto for lookalike messages  ·  medium value, small effort

**What.** e2b-sandbox.ts defines isSandboxGoneError() (narrow: the provider itself said the machine is dead) and isUnrecoverableSandboxError() (wider, includes legacy 404/not-found wording). Crucially, SHELL_MISSING_TARGET (/command not found|no such file|^path .* not found/i) is checked FIRST and vetoes the gone-classification, with the comment 'The same words from a live sandbox: a missing binary or a missing file inside it' and 'A missing binary or a missing file inside a live sandbox is not proof of death, so callers that persist "the sandbox is gone" must use this one.' Callers that merely decide whether to swallow a cleanup error may use the wide one; callers that persist a state change must use the narrow one.

**Why it beats the obvious alternative.** The single-predicate version conflates 'the machine is gone' with 'something in the machine was missing', and one `command not found` then permanently marks a healthy sandbox dead. Splitting by consequence — how confident must I be before I write this down? — is a better axis than splitting by error type, and the veto pattern (a matching phrase that disqualifies a classification) is the part that is easy to omit and expensive to omit.

**For us, in Swift.** In the verify step of the agent loop, classify failures with two predicates rather than one, named after their consequence: `isRetryable(_:)` versus `shouldRecordPermanentFailure(_:)`. Put the veto patterns first in the stricter predicate and comment why each one is a lookalike. Concretely for Bot-Harness: a `zsh: command not found` from a shell tool must not be allowed to mark the executor or the whole machine unhealthy, and an accessibility API failure on one element must not be recorded as 'Accessibility permission revoked'.

#### SSRF-hardened bring-your-own model endpoint  ·  medium value, medium effort

**What.** openai-compatible-url.ts normalises the base URL (rejecting non-http(s), rejecting embedded credentials, forcing a /v1 suffix), blocks cloud metadata hosts (169.254.169.254, metadata.google.internal) and link-local addresses outright, and classifies the hostname as private or public. pi-openai-compatible-provider.ts then wraps fetch with a DNS-pinned lookup that requires consistency: a hostname the user described as private must resolve only to private, non-link-local addresses, and a public hostname must not resolve to a private one. Redirects are refused (`redirect: "error"`), the /models probe reads at most 64 KB with a 5-second timeout and caps ids at 500 entries of 256 characters.

**Why it beats the obvious alternative.** Letting the user type a model base URL is the single most obvious way to turn an agent into a request forwarder into the local network. The DNS consistency check is the piece almost everyone skips: validating the hostname and then calling fetch leaves a window where the name resolves somewhere else. The bounded /models read is the other easy miss — a hostile endpoint otherwise streams unbounded JSON into memory during what the user thinks is a connection test.

**For us, in Swift.** Bot-Harness will want an Ollama / LM Studio / custom-endpoint brain adapter, and this is the checklist for it. URLComponents validation up front (scheme, no user/password, reject metadata and link-local hosts), then a URLSession delegate refusing redirects, a hard byte cap and timeout on the model-list probe, and a rule that any host outside 127.0.0.1 and the LAN requires an explicit user opt-in. The threat here is not a hostile user, it is prompt injection persuading the agent to point the endpoint somewhere; the check has to sit below the agent, in the same layer as the safety floor.

- ManagedConnectorProvider and the OAuth catalog machinery (Composio, Pipedream) — begin/complete/revoke, catalog(), listConnectedExternalIds(), connectionReady() plus a pending/connected row per workspace. This is an end-user app-directory for a hosted product; a single-user Mac app should put OAuth tokens in the Keychain and skip the connection lifecycle entirely.
- The multi-tenant fields threaded through every port: AdapterContext.workspaceId and userId, and the workspaceId scoping on every Prisma query. In a single-user local app these are a constant, and carrying them makes every signature wider for no benefit. Keep operationId, traceId, botId, runId and the cancellation token; drop the tenancy.

- AdapterRegistry in packages/adapter-kit/src/registry.ts: a Map<string, unknown> keyed by string slot names with an unchecked cast in get<T>(). Shipping fake backends selectable by env string is reasonable for a hosted service with a demo mode; for Bot-Harness a fake executor belongs in tests, not in the provider menu.

### Surprises

- adapter-kit is not a plugin SDK. There is no dynamic loading anywhere — I grepped for `await import` and `createRequire` across both packages and found only lazy imports of npm packages (sharp, jsdom), never of an adapter. Every provider is compiled into packages/adapters and selected by a `switch` on an environment string. 'Choose your own model and sandbox' is a build-time menu with a runtime selector, not an extension point. For Bot-Harness this is reassuring: Swift protocols plus a switch is not a lesser version of what they built, it is the same thing.
- The ModelProvider interface — `describe(): AdapterDescriptor<{ catalog: boolean; byok: boolean }>` and `listModels()` — has zero implementations in the repository. They wrote essentially no model-provider code: the catalog comes from the third-party @earendil-works/pi-ai package's builtinModels(), and their contribution is two synthetic providers registered into it (local Ollama/LM Studio from env vars, and an OpenAI-compatible placeholder the user fills in). The real seam for swapping model behaviour is AgentRuntime (run/abort over an AsyncIterable of events), not ModelProvider. Bot-Harness's Gemini brain adapter is at the AgentRuntime layer, which is the right layer.
- `contractVersion: "1"` appears on all twenty-one describe() implementations and is read by nothing. Grepping for reads of `.contractVersion` returns only the type declaration. Versioned-looking metadata that nothing validates is worse than no metadata: it reads as a compatibility guarantee that does not exist.
- The desktop provider — the one that runs on the user's own Mac, which is the closest analogue to all of Bot-Harness — is the LEAST capable backend in their model. It reports `graphical: false` and `takeover: false`, and its observe() returns a hard-coded 1x1 PNG placeholder with a text label instead of a screenshot. Their architecture treats the user's real machine as a filesystem and shell only. Bot-Harness's whole premise (ScreenCaptureKit, CGEvent, the accessibility tree on the real Mac) is the part they explicitly did not build, so there is no prior art here to borrow for the executor itself — only for the contract around it.
- The desktop provider's path containment is far more paranoid than its capabilities suggest, and it is the most safety-relevant code in the package. openContainedWorkspaceFile() opens the parent as a directory handle, opens the child with O_NOFOLLOW relative to that fd (via /proc/self/fd on Linux, NT relative opens on Windows), then verifies dev/ino/nlink agreement between the open handle, an lstat of the same path, and a re-open through the realpath — with an explicit comment that it re-stats the write handle LAST 'so a hardlink planted during verify cannot make an outside inode appear to live under the restored parent'. It requires nlink === 1 to reject hardlinks, and on failure only unlinks the created file if the path still names the inode it created. Bot-Harness's safety floor should assume this level of adversarial care around any path-based write rule, because 'is this path under the allowed root' is not answerable by string comparison on a live filesystem.
- Tool-name collisions across connectors are resolved by a composite that is itself a ConnectorProvider. ConnectorRegistry (in composio-connector.ts, oddly) discovers from all providers in parallel, swallows a failing provider's error as an empty list, and on a name clash renames to `connectorId.toolName` and then `connectorId.toolName.2`. It attaches a `route: { connectorId, toolName, resourceId? }` to each tool, with the comment 'In-process routing metadata. It is never exposed to the model.' The model sees a flat, deduplicated namespace; dispatch happens on the hidden route. This is directly relevant to Bot-Harness's MCP client plus capability router, where two servers will eventually both offer a `search` tool.

## How rakazo drives a computer: control server, action vocabulary, screenshots, coordinates, live view

### How it works

The agent-facing surface is two tools, computer_observe and computer_act, declared in packages/adapters/src/builtin-tools.ts. computer_act takes up to 24 ordered actions plus observe and settle_ms, so one model turn is one batch of input followed by one screenshot rather than a screenshot per click. parseComputerActions in packages/adapters/src/computer-tools.ts translates the model vocabulary (click, move, down, up, type, key, scroll, wait) into the internal ComputerAction union in packages/adapter-kit/src/types.ts; a double click is just the same pointer action emitted twice, and type is rewritten to kind clipboard, which despite the name compiles to xdotool type and never touches the X clipboard. The executor (packages/adapters/src/executor.ts, formatObservation near line 1050 and the computer_act branch at 1376) keeps one mutable lastComputerFrameId per run; observationToolResult compares it against the new frameId and, when equal, returns text saying the screen is unchanged with the image omitted entirely. frameId is sha256 of the PNG bytes, computed adapter-side in computerObservation in packages/adapters/src/computer-support.ts. Inside the container, infra/sandboxes/computer/control.py is a 268-line ThreadingHTTPServer on port 7070 with exactly one route, POST /v1/desktop, authenticated with hmac.compare_digest against RAKAZO_COMPUTER_CONTROL_TOKEN; the body is display, steps, observe, settleMs, and each step is either a waitMs or a literal argv command line. Its most interesting property is allowed_control_argv and allowed_xdotool_argv: the server re-validates the exact argv shapes it is willing to run (argv[0] must be env, argv[1] must be DISPLAY= plus the locked display, then only a closed set of xdotool forms, xdg-open with exactly one argument, or a binary from a two-name allowlist), so a compromised supervisor still cannot run arbitrary commands on the desktop. Those argv arrays are built one layer up by containerActionStep in infra/sandboxes/supervisor/src/supervisor-logic.ts and xdotoolCommand in infra/sandboxes/supervisor/src/computer-spec.ts, which also maps friendly key names (enter, esc, cmd) to X keysyms. The whole request is taken under a per-display lock, so a batch and its trailing observation are atomic against other callers, and after the steps it sleeps settleMs (clamped to 5s) before capturing. Capture itself has a fast path and a fallback: NativeCapture loads /usr/local/lib/librakazo-xcapture.so via ctypes and calls rakazo_xcapture_png, which keeps a persistent MIT-SHM XImage attached to the root window (allocate_image, XShmGetImage) and encodes PNG in-process at compression level 3; if the library or shared memory is unavailable it shells out to ImageMagick import -window root. The C file infra/sandboxes/computer/xcapture.c exists to avoid two costs Python cannot avoid: re-creating an X image and copying the full framebuffer through a subprocess on every frame, and PNG-encoding it out of process. It also exposes rakazo_xinput_argv, which reimplements the same handful of xdotool commands directly with XTest (XTestFakeKeyEvent, XTestFakeMotionEvent, XTestFakeButtonEvent) so a click costs no fork, and rakazo_xcapture_damage, which subtracts an XDamage region and returns one bounding rectangle of what changed. Every observation carries image, mimeType, width, height, cursor position and the active window id and title, harvested with xdotool getdisplaygeometry, getmouselocation --shell and getactivewindow. The screen is a fixed 1280x800 Xvfb (DEFAULT_COMPUTER_SCREEN in packages/core/src/teach-recording.ts) and the screenshot is never downscaled, so the model's pixel coordinates are 1:1 with the framebuffer and no transform exists anywhere in the action path. The live view is entirely separate from the agent path: start.sh runs x11vnc with -viewonly behind websockify and a trimmed noVNC page, infra/sandboxes/computer/embed.html, which the web app loads in an iframe with pointerEvents none (apps/web/src/pages/Shell.tsx). Human control is a different channel, not a flag: interactiveScreenCommand in supervisor-logic.ts starts a second, non-viewonly x11vnc plus websockify pair on a different port, stamped with a control token file, and kills it when the lease ends; apps/web/src/screen-proxy.ts additionally rewrites view_only on the URL server-side from an HMAC-signed path segment so the client cannot ask for control by editing a query string. When a human demonstrates a task, TeachCaptureOverlay.tsx maps browser pointer coordinates back to screen coordinates through mapTeachPointer, which reproduces noVNC's aspect-fit letterbox, and coalesces pointer moves to one in flight while guaranteeing the final position lands before the button release.

### Patterns worth taking

#### Batched action program with one trailing observation  ·  high value, medium effort

**What.** computer_act accepts up to 24 ordered actions (click/move/down/up/type/key/scroll/wait) plus observe:boolean and settle_ms. The whole batch runs under one display lock, then sleeps settle_ms, then captures once. The tool description tells the model to batch only predictable actions and stop before an outcome it needs to inspect.

**Why it beats the obvious alternative.** One screenshot per click is the default shape of computer-use agents and it is what makes them slow and expensive. Making the unit of work a small program rather than a single event cuts round trips by roughly the batch size on predictable sequences (click field, type, press Enter), and settle_ms encodes the wait-for-UI problem in one place instead of the model guessing sleeps. The 24 cap and the 5s clamp keep a runaway batch bounded.

**For us, in Swift.** Define ComputerAction as a Swift enum with associated values and ComputerActionBatch { actions: [ComputerAction], observe: Bool, settleMs: Int }. The macOS executor iterates the batch posting CGEvents, holds an actor lock for the batch so the trace and the screenshot cannot interleave with another tool call, then sleeps and takes one ScreenCaptureKit frame. Enforce the cap and clamp at the boundary, not in the brain. Permission checks stay per-action inside the loop, which fits the existing floor plus rules model.

#### Content-hash frame id, and dropping unchanged screenshots  ·  high value, small effort

**What.** Every observation carries frameId = sha256(png). The executor remembers the last frameId of the run; if the new one matches, the tool result is text only, saying the screen is unchanged, and the image is dropped.

**Why it beats the obvious alternative.** A screenshot is by far the largest thing in an agent's context. Failed clicks, no-op keystrokes and waits produce byte-identical frames surprisingly often, and re-sending them costs tokens, latency and money while teaching the model nothing. Hashing the encoded bytes is exact, needs no image comparison, and the id doubles as a stable handle for logs and traces.

**For us, in Swift.** Hash the PNG with CryptoKit SHA256 (Apple SDK, no dependency) at capture time, store it on the Observation struct, and keep lastFrameId on the run. When it repeats, emit the text plus metadata and skip the image part. The hash also gives the hash-chained trace a natural content address for screenshots stored as PNG on disk, so repeated frames can be stored once and referenced.

#### Shape allowlist at the execution boundary, independent of the caller  ·  high value, medium effort

**What.** control.py does not trust the supervisor that authenticated to it. allowed_control_argv checks argv length, types, NUL bytes, per-arg length, that the display matches the one the request locked, and then matches each command against a closed set of literal shapes: xdotool key with exactly --clearmodifiers plus one combo, mousemove with integer coordinates, click with --repeat 1..20 on button 4 or 5, xdg-open with exactly one argument, or a launch binary from a two-name set with no slash in it.

**Why it beats the obvious alternative.** It is a second, dumber gate that assumes the smart layer above it is compromised or buggy. The interesting move is that it validates shape, not intent, so it can be read and verified in one sitting, and no amount of prompt injection upstream turns it into a shell. This is the same architectural idea as an unlowerable safety floor, but applied at the point where an action becomes a real system effect.

**For us, in Swift.** Put a validator in the macOS executor that sits below the capability router and the permission engine: given a ComputerAction it re-derives what CGEvent or AX call it will make and refuses anything outside an enumerated set (coordinates within the current display bounds, key codes from a known table, modifier sets from a known table, scroll deltas clamped). It should not consult the permission rules or the brain output at all; it is a pure function of the action. Log every rejection to the trace with the reason.

#### View and control as two separate channels, not one flag  ·  high value, medium effort

**What.** The always-on live stream is x11vnc with -viewonly on one port and cannot accept input at all. Human takeover starts a second, separate x11vnc plus websockify pair on a different port, tagged with a control token file, and interactiveScreenCommand kills it when the lease expires. The web proxy also rewrites the view_only parameter server-side from an HMAC-signed path, and the iframe carries pointerEvents:none until the lease is held.

**Why it beats the obvious alternative.** A boolean on a shared stream is one bug away from being flipped. Two processes means the read-only path has no code path to input, and revocation is a kill rather than a state change, which is verifiable from outside (the port stops answering). The lease has a TTL and an expiry job, so control lapses on its own rather than depending on a release call.

**For us, in Swift.** Bot-Harness has no VNC, but the same split applies to the activity window: make the live view a pure SCStream render that has no input handler compiled into it, and make taking control a distinct object with a TTL that swaps in a different view (or enables a separate input responder) and pauses the agent loop. When the lease expires, tear the input view down rather than setting a disabled flag. Record lease acquire and release in the trace as first-class events.

#### Letterbox coordinate mapping plus move coalescing for human demonstration  ·  medium value, small effort

**What.** mapTeachPointer (packages/core/src/teach-recording.ts) maps a click in the displayed view back to screen coordinates by reproducing the viewer's aspect-fit scale and centring offsets, then clamps to width-1/height-1. TeachCaptureOverlay keeps at most one pointer move in flight and one pending, dropping intermediate positions, but always enqueues the final position before the button-up, with a comment saying a release at a stale position is not acceptable.

**Why it beats the obvious alternative.** Every UI that shows a scaled remote screen and lets a human point at it gets the letterbox wrong at least once; centring offsets, not just scale, are the part people forget. The move coalescing is the right answer to a stream of pointer events feeding a slower transport, and the exception for the last move before release is the non-obvious correctness detail that makes drags work.

**For us, in Swift.** Bot-Harness already has a real display, so the mapping is between the activity window's rendered frame and CGDisplay coordinates, which is the same aspect-fit maths (scale = min(w/sw, h/sh), offsets = (w - sw*scale)/2). Do it once in a small value type with tests rather than inline in the view. If Bot-Harness ever records a human demonstration to build a routine, copy the coalescing rule verbatim, including the flush-before-release.

#### Capability gating and self-preservation guards on the computer tools  ·  high value, small effort

**What.** Two guards, both in packages/adapters/src/executor.ts. filterImageReturningComputerTools removes computer_observe, computer_act, open_path and launch_app from the tool list entirely when the selected model has no image input (modelAcceptsImageInput in model-vision.ts), with a clear error string if one is somehow called. isProtectedComputerLifecycleCommand blocks the shell tool from running kill, pkill, killall, xkill, systemctl stop/restart and, notably, returns dynamic (meaning block) for eval, source and dot, and for any command it cannot statically tokenize.

**Why it beats the obvious alternative.** The first prevents a whole class of confusing failures where a text-only model clicks blindly at hallucinated coordinates. The second stops the agent from killing the browser, X server or VNC that constitute its own eyes and hands, which is a real failure mode when an agent tries to fix a stuck app. Failing closed on commands it cannot parse is the correct default and is cheap.

**For us, in Swift.** Register the screen tools in the capability registry conditionally on the configured brain declaring image input, and have the capability router return an explicit refusal rather than a missing-tool error. For the shell/process manager, add a small static classifier that fails closed on unparseable command lines and blocks anything that would kill Bot-Harness itself, its helper processes, WindowServer, or revoke its own TCC grants. Put it below the permission rules so a permissive user rule cannot open it.

### Not applicable to us

- The whole X11 runtime picture (Xvfb, fluxbox with a maximize-Chromium apps file, xterm, x11vnc, websockify, noVNC, dbus, xdg-mime registration in start.sh) exists to manufacture a desktop that does not otherwise exist. Bot-Harness has a real logged-in Mac desktop, so none of it transfers.
- xcapture.c as such. Its purpose is a persistent MIT-SHM XImage plus in-process libpng encoding to avoid per-frame subprocess and copy costs. ScreenCaptureKit already gives a persistent stream of IOSurface-backed frames and CGImageDestination handles encoding, so the C layer solves a problem the macOS SDK has already solved.
- clipboard-bridge.js. It is a workaround for Debian noVNC 1.3 not syncing the clipboard from a chrome-less embed and for macOS Cmd+V arriving as Super+V over RFB. Both are artefacts of RFB in a browser.
- The multi-screen allocator (screenPorts, TEAM_SCREEN_LIMIT of 8, nextScreenIndex, screen leases, ensureScreenCommand booting a whole extra Xvfb/fluxbox/Chromium/x11vnc stack per screen). This exists so several team bots share one container. Single-user, single-display Bot-Harness has one screen by definition.
- Per-bot Docker networks (computerNetworkNameFor, ensureBotNetwork) and the container hardening in containerCreateOptions (CapDrop ALL, no-new-privileges, PidsLimit, ReadonlyPaths). Real isolation work, but it is isolation between tenants on a shared host.
- The docker-exec fallback path (a Python one-liner passed to container.exec that replays the same argv steps, plus observeContainer shelling out to ImageMagick and base64). It is redundancy for when the in-container HTTP service is unreachable; an in-process macOS executor has no equivalent transport to lose.
- The signed screen proxy (apps/web/src/screen-proxy.ts, HMAC path signatures, AES-GCM encrypted remote targets, header stripping). It solves getting a container's VNC port to a browser across a network boundary. A local SwiftUI window has no such boundary.
- Bearer-token auth on the control server, and the lease fencing machinery (leaseId, fence, canTakeScreenLease). These exist because several worker processes can race for one desktop. One local app with one Store does not need them, though the TTL idea inside the takeover lease is still worth keeping.

### Surprises

- The Electron/desktop provider explicitly cannot drive the host GUI. DesktopSandboxProvider.describe() in packages/adapters/src/desktop-sandbox.ts returns graphical:false, takeover:false, and its observe() returns placeholderObservation, a 1x1 PNG. Its act() calls applyPlaceholderAction, which just stores a string like the action's kind in an in-memory box. So the run-on-your-own-machine mode is shell and files only; every real computer-use capability in this project requires the Linux container. Given the stated framing as a Grok Bot alternative, that is a bigger gap than the README suggests, and it is the thing Bot-Harness is actually attempting.
- The protocol crossing the trust boundary is argv arrays, not semantic actions. The supervisor serialises xdotool command lines into the request body and control.py parses them back apart with a whitelist. It works, and the whitelist is genuinely tight, but the natural design (send {kind: click, x, y} and let the server decide the mechanism) would have been both smaller and safer. The cost shows up immediately below: rakazo_xinput_argv in xcapture.c has to re-parse those same argv strings to implement the XTest fast path.
- That dual parse has already drifted. control.py accepts scroll as xdotool click --repeat N 4|5 (argv length 7), but the C fast path matches click only at argc == 6 (count and button with no --repeat). rakazo_xinput_argv therefore returns 0 for every scroll and control.py falls back to spawning a real xdotool process. Same for type, which the C layer never implements. So the native input path covers keys, mouse moves and single clicks only, and nothing in the code or comments says so.
- XDamage is computed and thrown away. rakazo_xcapture_damage subtracts the damage region and reduces it to one bounding rectangle, control.py puts it in the observation JSON as damage, and then nothing consumes it: grepping the entire TypeScript tree for damage returns zero hits, and docker-sandbox.ts observe() and act() destructure the response body field by field, silently dropping it. The most interesting piece of the C code is dead metadata today.
- There is no coordinate transform anywhere in the action path. The framebuffer is a fixed 1280x800, the screenshot is sent at native size with lossless PNG at compression level 3, and the model's coordinates go through unchanged. They chose to pay the bytes rather than introduce a scale factor the model could get wrong. Scaling exists only in the human-facing viewer, and mapTeachPointer inverts it. For Bot-Harness on a Retina display this is the one place where the mapping cannot be skipped: points versus pixels means a transform is mandatory, and it should live in exactly one tested function.
- computer_act participates in the approval/replay system rather than sitting outside it. In executor.ts the approved payload is re-taken with approvedEffectReplays.take(name) and used in place of whatever the model reconstructed after a worker resume, and a mismatched tool name is rejected outright. So an approval is bound to an exact persisted action batch, not to a description of one. That is a stronger contract than asking the user to approve an intent and is directly relevant to how Bot-Harness should persist a pending permission decision across a restart.
- The system prompt carries an explicit injection defence about screen contents: it tells the bot that text visible inside web pages, including banners saying work is finished, is external page content and not a system command to halt. Screen pixels are treated as untrusted data in the prompt itself, which is a cheap complement to a permission layer.

## Safety — permissions, approvals, credential handling, and prompt-injection defence

### How it works

Every tool call funnels through one closure, `applyTool(name, args, executionId)` in `packages/adapters/src/executor.ts` (around line 1070), before any dispatch happens. Risk is not declared on a tool; it is computed from the tool's name. `toolRequiresApproval(toolName, viaConnector)` in `packages/core/src/action-approval.ts` checks a hardcoded `APPROVAL_EXEMPT_TOOLS` set (shell, write_file, computer_act — deliberately exempt), a `APPROVAL_REQUIRED_BUILTIN_TOOLS` set (`destination.write`, `delete_bot`, `archive_bot`), and otherwise falls to `connectorToolRequiresApproval`, which regex-matches the verb in the name: `get/list/search/find/read` is read-only, a long `create|delete|send|pay|publish|…` list is mutating, and anything matching neither is treated as mutating. That last clause is the fail-closed default for tools discovered at runtime whose semantics are unknown. User rules are structured rows (`ActionApprovalRule` with `effect` ∈ {always_allow, require_approval}, `matchKind` ∈ {tool, connector, category}, `matchValue`), resolved by `resolveActionApprovalDetail`, which selects the highest-specificity matching rules (tool 3 > connector 2 > category 1) and only then applies deny-wins within that tier. `planActionGate` combines rule resolution with an optional second-model judge: rules always win, and only the unmatched "default" path may call the judge. The judge (`packages/adapters/src/auto-review.ts`, `runAutoReviewJudge`) is a separate cheap model with a 1.5s `AbortSignal.timeout`, no tools, given redacted args and asked for `{"decision":"pass"|"ask"}`; `applyJudgeDecision` makes it one-directional — it can escalate to ask but can never turn an ask into an allow, and a timeout or unparseable reply becomes "ask" on consequential tools. When approval is needed, the run does not suspend in memory. `recordEffect` writes an `ExternalEffect` row with status `intended` and a unique `idempotencyKey` = `approvalEffectKey(runId, toolName, sha256(stableJsonValue(args)))`; `pauseRunForInput` (`packages/db/src/events.ts`) transactionally flips the run to `waiting_input`, drops the worker lease, posts an ask card built by `buildApprovalAskBlock`, and the tool returns `{terminate: true}` so the whole process unwinds and exits. The human answers in the web or mobile ask card; `answerRunInput` flips the effect to `approved` or `denied` and re-queues the run. The next worker re-runs the task from the top, loads `externalEffect where status = approved`, and builds two things: a prompt suffix from `buildApprovalContinuation` telling the model to call exactly those requests in order, and an `ApprovedEffectReplayQueue` (`packages/adapters/src/approval-effect.ts`) that enforces it — `applyTool` rejects a call whose name is out of order and overwrites `args` with the persisted approved payload, so an argument the model reconstructs differently never executes. `resolveDuplicateEffectGate` handles every replay case, including an `executing` row left by a crash, which becomes status `uncertain` and returns an error telling the model the outcome is unknown and it must verify the destination rather than retry. Secrets never enter the model's context: the `request_secret` tool pauses the run for a masked field, the plaintext is stored AES-256-GCM encrypted (`packages/adapters/src/secrets.ts`, with the record id as AAD), and on resume the executor decrypts it, pushes it onto a per-run `runSecrets` array, and hands it straight to the connector — the model only ever sees `{ok: true, submitted: true}`. Every text path out of the run passes through `redactSecrets` or `createStreamingRedactor` (`packages/core/src/events.ts`), which buffers the trailing `maxSecretLength - 1` characters so a secret split across stream chunks cannot leak. Prompt-injection defence is layered: one system-prompt sentence at executor.ts:2370 declaring tool output untrusted, plus HTML-escaping and explicit `<untrusted>` delimiting of every channel where derived content re-enters the prompt at a privileged position (compaction summaries and recalled memory in `history-compaction.ts`, peer-bot messages in `buildBotMessageWakePrompt`, scratchpad items, and the judge's own prompt). Separately, `isProtectedComputerLifecycleCommand` (executor.ts:290) parses shell commands with a real tokenizer, expands a fixed table of known env vars, and returns "dynamic" — meaning blocked — for backticks, command substitution, unknown `$VAR`, or a parse failure, recursing into any `bash -c` payload it finds.

### Patterns worth taking

#### Durable effect ledger with an explicit 'uncertain' state  ·  high value, medium effort

**What.** Before a consequential tool runs, a row is written with status `intended`, a unique idempotency key, and the full request JSON. It moves intended -> approved/denied -> executing -> completed. A row still marked `executing` when the run restarts is settled to `uncertain`, and `uncertainEffectResult()` returns to the model: the earlier call's outcome is unknown, it was deliberately not replayed, verify the destination before proposing another action. `resolveDuplicateEffectGate` in packages/adapters/src/approval-effect.ts is the pure function that maps every stored status onto execute / return-cached / pause / uncertain.

**Why it beats the obvious alternative.** Our trace writes `toolProposed` then `complete(step, outcome:)`, which records intent but cannot act on it. If Bot-Harness is killed between sending an email and writing the completion, the next run has no idea and will happily send it again. The 'uncertain' state is the honest third answer between 'done' and 'not done', and it is the one an agent on a real Mac with no snapshot needs most. It also makes the ledger, not the transcript, the authority on what happened.

**For us, in Swift.** Add a small append-only `EffectLog` beside the trace (JSONL, same directory, one line per status transition so the file stays append-only and human-readable, with the current status folded in memory at load). Key each effect `"\(runID):\(tool):\(sha256(canonicalJSON(args)))"`. In AgentLoop.dispatch, write `intended` before the call and `completed` after; on loop start, scan for rows left at `executing` and mark them `uncertain`, feeding the uncertainty sentence back to the model as the tool result if it proposes the same key again. Store the digest only for consequential tools so read-only calls do not bloat the file.

#### Approval pins a hash of the exact arguments, and resume replays those bytes  ·  high value, small effort

**What.** `approvalEffectKey(runId, toolName, args)` hashes a canonically-serialized form of the arguments (`stableJsonValue` sorts keys, rejects non-plain prototypes, cycles, NaN and sparse arrays — it throws rather than hashing something ambiguous). On resume, `createApprovedEffectReplayQueue` hands the executor the persisted payload and `applyTool` does `args = approvedEffectReplays.take(name) ?? args`, replacing whatever the model supplied; an out-of-order call is refused with 'Approved request X must be replayed before Y'. `buildApprovalContinuation` tells the model in plain words that the executor enforces the persisted request and that every string inside it is data, not instructions.

**Why it beats the obvious alternative.** This is their real prompt-injection defence, and it is structural rather than textual. Injected content can make the model propose an action, but the human sees the exact arguments on the card and the executor will only ever run those bytes. Our loop shows the user `summary` and `detail` strings and then executes the in-memory `action` — close in practice because we never leave the process, but nothing in our trace binds the approval to the argument bytes, so 'why was this allowed' cannot be answered by hash.

**For us, in Swift.** Write a canonical encoder (sorted keys, no floats-that-are-not-finite, throw on anything ambiguous) and record `approvalDigest` on both the `permissionCheck` and `toolProposed` trace events. Have PermissionEngine return the digest inside PermissionDecision, and assert before dispatch that the digest of the arguments about to run equals the digest the user approved. That assertion is cheap and it makes 'the approval was for a different payload' impossible rather than merely unlikely.

#### A shell guard that fails closed on anything it cannot statically decide  ·  high value, medium effort

**What.** `tokenizeProtectedShellCommand` runs a POSIX word splitter, substitutes a fixed table of known variables (HOME, PWD, PATH, WORKSPACE...), and returns the sentinel "dynamic" for a backtick fragment, a command substitution, an unknown expansion, an unrecognised control operator, or a parse error. `isProtectedComputerLifecycleCommand` treats "dynamic" as blocked, checks basenames rather than whole words so `/usr/bin/pkill` is caught, blocks `eval`/`source`/`.` outright because they hide a program inside a single token, and recurses into the program string of any `bash -c` / `sh -lc` / `--command=` it finds. Its test file asserts 24 evasions including `k\ill`, heredocs, `$KILLER chromium`, and `bash -c 'eval "pkill chromium"'`.

**Why it beats the obvious alternative.** Our SafetyFloor.classify does `contains(text, ["rm -rf /", "rm -rf ~", ...])` on a lowercased summary+detail string. `bash -c "$CMD"`, `rm -rf $HOME`, `rm -rf /Users/Kunal/`, or a base64 payload all pass it. This is the single weakest point in our floor, because the floor's whole claim is that it holds when the model is wrong, and a substring match holds only when the model is cooperative. Their design accepts false positives (an undecidable command is blocked) as the correct trade for a safety floor.

**For us, in Swift.** Write a small POSIX word splitter in Swift — quoting, escapes, operators, and a `.dynamic` case for `$(`, backticks, unknown `$VAR`, and parse failure. Expand only a fixed table (HOME, PWD, TMPDIR, the bot workspace). Feed the resulting words, basename-reduced, into the floor classifier instead of the raw string, and recurse into `-c` payloads. Keep the substring check as a second net, never as the first. No dependency needed; this is a few hundred lines and it is exactly the kind of code CLAUDE.md says to slow down on.

#### A one-directional second-model reviewer on the default path  ·  high value, medium effort

**What.** When no user rule matches and the tool is consequential, a cheap separate model is asked, with a 1.5s timeout, no tools, and redacted arguments, whether the action looks surprising relative to the user's stated task. `applyJudgeDecision` maps its answer onto ask/allow such that it can only escalate: pass -> allow, ask -> ask, error or timeout -> ask on anything consequential. `planActionGate` keeps it strictly subordinate to rules, so the judge can never override an explicit user decision, and its verdict is persisted on the effect row (`reviewDecision`, `reviewReason`, `reviewModel`) so a replay reuses it instead of paying for it twice. `buildAutoReviewPrompt` HTML-escapes and delimits the args, task and bot description and tells the judge the blocks are data.

**Why it beats the obvious alternative.** It closes the gap our natural-language rules leave without weakening determinism. The verdict is fail-safe by construction, so a broken or slow checker degrades to more prompts rather than fewer. The persistence of the verdict on the effect row is the part that is easy to miss and matters: without it, a replayed run re-asks a model and can get a different answer for an action the user already saw.

**For us, in Swift.** Add a `Reviewer` step between PermissionEngine's `.allowed` outcome and dispatch, running only when `decidedBy == .defaultPolicy` and the tool writes. Reuse the Gemini adapter with a short timeout and a strict JSON reply, and enforce in the type system that it returns `ReviewVerdict { case pass, escalate }` with no allow case at all — so it is impossible to wire it up backwards later. Record the verdict and reason on the permissionCheck trace event, and surface the reason on the approval card the way `buildApprovalAskBlock` puts `reviewReason` at the top of the detail.

#### Secrets that never enter the model's context, and a chunk-boundary-safe redactor  ·  high value, medium effort

**What.** Two distinct tools with a deliberate split: `request_secret` collects a one-shot OTP or API key in a masked field, and `request_takeover` hands the physical screen to the human for passwords, 2FA, CAPTCHA, passkeys and payment. The tool description for `request_secret` explicitly routes website logins to takeover instead, and if the model asks for `purpose: "password"` with no connection to complete, the executor refuses to type it and returns the note 'Use request_takeover for website logins; the secret was not typed onto the computer.' The plaintext is decrypted only inside the executor, appended to a per-run `runSecrets` list, and passed straight to the connector. `createStreamingRedactor` withholds the last (longest secret length - 1) characters of the buffer so a secret straddling two stream chunks is still caught, and when a new secret is learned mid-run the old redactor's `finish()` tail is carried over rather than dropped.

**Why it beats the obvious alternative.** We store credentials in the Keychain, which is stronger at rest than their AES-GCM blob, but we have no equivalent of the injection path: a way for a credential to reach a destination without passing through the model's context or the transcript. The takeover-versus-secret split is also the right product answer for a real Mac — a password for a website should be typed by the human, not synthesized into CGEvents. And the streaming redactor is the detail everyone gets wrong; token-by-token redaction that only checks the current chunk leaks on the boundary.

**For us, in Swift.** Add two tools mirroring theirs. `requestSecret` suspends the loop for a masked SwiftUI field, writes the value to the Keychain under a run-scoped account, and hands it to the tool implementation directly — the tool result returned to the model is a fixed `{"submitted": true}`. `requestTakeover` is the floor's answer for `enteringCredentials`: unbind CGEvent posting, tell the user what to do, and resume on their signal. Then implement the boundary-buffering redactor as a struct with `push(_:) -> String` / `finish() -> String` and route every emit and every trace write through it, seeded from the run's secret list.

#### Escape and delimit every channel where derived content re-enters the prompt  ·  medium value, small effort

**What.** Summaries from history compaction, recalled long-term memory, scratchpad items, peer-bot messages, and the judge's own inputs are each HTML-escaped (`&`, `<`, `>`) and wrapped in a named tag with a sentence saying the block is untrusted historical data and never instructions — `buildBotMessageWakePrompt` additionally escapes CR/LF in the sender's name so a bot cannot forge a new prompt line out of its own display name. Notably, raw tool output is NOT wrapped; it gets only the one system-prompt sentence.

**Why it beats the obvious alternative.** These are the channels where attacker text gets laundered into a position of higher trust: a web page the agent read yesterday becomes 'memory', and memory reads like the system's own voice. Escaping the angle brackets is what stops the content from closing the delimiter it lives inside. Our compaction and memory paths have the same shape and, as far as this area of the code goes, none of this framing.

**For us, in Swift.** A single `func untrusted(_ text: String, tag: String, note: String) -> String` that escapes the three characters, strips CR/LF from any attribute value, and emits the tag plus the note. Apply it at every point where non-user text is composed into the prompt — memory recall, compaction output, MCP resource contents, accessibility-tree text, and OCR of the screen. Screen text is the one we have and they do not: what the agent reads off a window is exactly as untrusted as a web page.

#### TOCTOU-hardened workspace containment for file writes  ·  medium value, large effort

**What.** `isAllowedDesktopPath` does containment by `path.relative` rather than prefix comparison, so `/work-evil` cannot pass as inside `/work`. `localWorkspaceTarget` and `openContainedWorkspaceFile` in packages/adapters/src/desktop-sandbox.ts then walk and create each path segment from a held directory file descriptor, open the final file with O_NOFOLLOW, re-derive the realpath from the open fd rather than the name, and re-check the inode — and on failure they only rmdir a directory whose dev/ino match the one they created. The test file simulates a symlink swap landing between the lstat and the open.

**Why it beats the obvious alternative.** This is the one place their code is paranoid about an attacker who can write to the filesystem concurrently — which on a real single-user Mac is any process the user runs, including a previous agent action. String-level path checks are the standard implementation and they are wrong under a symlink race. Worth taking only if we decide workspace containment is a floor guarantee rather than a convention; if it is a floor guarantee, the string version does not deliver it.

**For us, in Swift.** Darwin exposes `openat`, `O_NOFOLLOW`, `O_DIRECTORY` and `fcntl(F_GETPATH)` directly from Foundation-free Swift, so this is expressible with no dependency. Resolve the workspace root once with `realpath`, then walk segments with `openat` from the held root fd, and verify the final fd's `F_GETPATH` still lies inside the root before writing. Do it for write, delete and rename; reads can stay on the cheap check.

### Not applicable to us

- The run lease and fence (`leaseOwner`, `leaseFence`, `renewRunLease`) exist so two workers cannot both own a run. We are one process; the durable-pause idea survives the translation, the lease does not.
- `answerRunInput` transactional resume via Postgres row locks (`SELECT ... FOR UPDATE` on the thread) — the concurrency it defends against does not exist for a single local app. Take the state machine, not the transaction.
- The `always` button creating a workspace-scoped rule attributed to `createdByUserId`, and the check `if (run.userId !== input.answeredByUserId) return null` that stops a teammate from creating a standing rule on someone else's run. Pure multi-user access control.
- `EncryptedSecretStore` (AES-256-GCM, scrypt, record-id-as-AAD, plus a legacy SHA-256 read path). Keychain with an access control on the item is strictly better on macOS and is already what we do. The only transferable idea is binding a secret to the identity it is stored under, which Keychain's service/account keying already gives us.
- `resolveSupervisorToken` / `resolveScreenProxySecret` / `resolveUpdaterToken` and their mutual-distinctness checks — these guard HTTP boundaries between sidecar containers. We have no boundary to guard.
- Container and remote sandbox providers (docker-sandbox, e2b-sandbox, daytona-sandbox, box-sandbox) as an isolation strategy. Their answer to 'the agent can break the machine' is a disposable container; ours is deliberately that there is no container, which is why our floor has to be stronger than theirs, not weaker.
- The `mcp_approval` card flow gated on OAuth browser sign-in. The mechanic worth keeping is much smaller: a newly added MCP server's tools stay unavailable until the human approves the server, and the server row records only which env var and header NAMES exist (`Object.fromEntries(keys.map(k => [k, true]))`) with values in the encrypted store.

### Surprises

- There is no safety floor. `ActionApprovalRule.effect` is only `always_allow` or `require_approval` — a user cannot express 'never', and nothing in the codebase can refuse an action outright. The strongest possible outcome is 'ask a human'. Our nine unlowerable categories have no counterpart anywhere in this repo.
- The default is allow, not ask. `resolveActionApprovalDetail` returns `{decision: "allow", source: "default"}` when no rule matches, and `planActionGate` turns that into a real execution unless Auto Review is both enabled and configured. With no rules and the judge off, a connector tool named `gmail_send_email` runs with no human in the loop. There are no seeded default rules; the settings UI offers exactly two opt-in presets, email and purchase. Approval is opt-in, which is the opposite of what the marketing framing implies.
- `shell`, `write_file`, `computer_act` and `launch_app` are all in `APPROVAL_EXEMPT_TOOLS` — the tools with the widest blast radius are the ones that never ask. That only makes sense because they run inside a disposable container; it is precisely the assumption we do not get to make.
- Conflict resolution is specificity-first, not deny-first. `resolveActionApprovalDetail` picks the highest-specificity tier and applies 'require_approval wins' only within that tier, so a tool-level `always_allow` silently beats a connector-level `require_approval`. Our deny-wins-globally rule is the stricter of the two, and the difference is not obvious from either UI.
- The audit record stores the raw request. `recordEffect` writes `args` unredacted into `externalEffect.request`, and `redactSecrets` is applied only on the display and message paths (`buildApprovalAskBlock`, `redactBlocks`, progress streaming). Their strongest secret hygiene is on the way out to the human, not on the way in to the record — the inverse of our rule that secrets are redacted on the way into the trace.
- Their prompt-injection defence for raw tool output is one sentence at executor.ts:2370 and nothing else. No filter, no classifier, no delimiting of web pages or emails. The escaping and `<untrusted>` wrapping is reserved for content the system itself derived and re-injects — compacted summaries, recalled memory, peer-bot messages. They appear to have concluded that filtering injected text is not winnable, and put the effort into making the approval unforgeable instead. That is a defensible position and it is worth deciding whether it is ours.

## Always-on behaviour: routines, schedules, events, monitors, notifications, and long-task survival

### How it works

Scheduled work is one Prisma model, `Routine` (packages/db/prisma/schema.prisma:520): `crons String[]`, `timezone`, `active`, `notify`, `webhookEnabled`, `lastRunAt`, `nextRunAt`, indexed `@@index([active, nextRunAt])`. A routine holds several cron expressions at once and `nextRunAt` is the nearest firing across all of them, computed by `nextCronDateAcross` in packages/core/src/cron.ts (the only third-party piece is `croner`). One-shot reminders reuse the same model through a sentinel cron string `"@once"` (`ONCE_ROUTINE_CRON`); `isOneShotRoutineCrons` treats a routine as one-shot only when it has exactly one cron and that cron is the sentinel, and `hasMixedOneShotSchedule` rejects mixing. Firing is a background job. `packages/adapter-kit/src/background-jobs.ts` defines six job names — `run.continue`, `routine.wakeup`, `computer.sleep`, `computer.control-expire`, `skill.teaching-expire`, `history.compact` — each with a Zod payload schema and, importantly, a `replaceKey` (`routine:<id>`, `run:<id>`, …) that makes re-enqueueing idempotent. Graphile Worker (packages/adapters/src/wakeup.ts, `GraphileJobPublisher`/`GraphileJobWorkerHost`) maps `replaceKey` onto Graphile's `jobKey` and `availableAt` onto `runAt`; the same file ships `InMemoryJobQueue`, a ~45-line `setTimeout`+`Map<key,timer>` implementation of the identical `JobPublisher`/`JobWorkerHost` interfaces (test-only per CONTRIBUTING.md:41, but functionally complete). What makes the queue replaceable is `createJobReconciler` (packages/adapters/src/job-reconciler.ts): every 30 seconds it queries the database for runs that are `queued` or whose `leaseExpiresAt` has passed, routines that are `active` with `nextRunAt <= now + 60s`, and computers with an expiring control lease, and re-enqueues the corresponding jobs. The queue is an accelerator; durable rows are the truth. Actual firing is a compare-and-swap: `wakeRoutine` (packages/adapters/src/executor.ts:482) returns early unless `routine.nextRunAt` equals exactly the `scheduledFor` in the payload, then inside a transaction does `updateMany({ where: { id, active: true, nextRunAt: scheduledAt }, data: { lastRunAt: now, nextRunAt: <recomputed> } })` and only creates the Task+Run if `updated.count === 1`. The next occurrence is computed from `Math.max(Date.now(), scheduledAt)`, so a routine missed while the machine was off fires exactly once on return and then resumes from now rather than backfilling every skipped slot. A run survives crashes through a lease, not through queue durability: `Run` carries `leaseOwner`, `leaseFence` (monotonic int) and `leaseExpiresAt`; `continueRun` (executor.ts:591) claims with a conditional `updateMany` matching either a resumable status or an expired lease, sets a 5-minute lease, and runs a 60-second `setInterval` heartbeat calling `renewRunLease`; if the renew updates zero rows the worker sets `leaseValid = false` and aborts its own AbortController. Every write during the run is guarded by `where: { leaseOwner, leaseFence }`, so a resurrected zombie worker cannot write. Legal statuses and transitions are declared as data in packages/core/src/run-state.ts (`ACTIVE_RUN_STATUSES`, an `allowed` map, `assertTransition`, `nextFence`); `waiting_input` and `waiting_takeover` are durable parked states with no worker attached. Deadlines are also enforced lazily: `packages/adapters/src/teaching-session.ts` checks `expiresAt <= Date.now()` at lines 152/536/560/586 on every read, so the `skill.teaching-expire` job only makes expiry timely, never correct. Events are an append-only `Event` table with a per-thread monotonic `seq` and a 41-value `ProductEventType` enum (packages/contracts/src/events.ts) covering thread/run/computer/routine/skill/bot lifecycle. PostgreSQL LISTEN/NOTIFY (packages/adapters/src/realtime.ts) carries only a topic envelope, never the data — `followThreadEvents` (packages/db/src/events.ts:869) uses a `ChangeLatch` that is woken either by NOTIFY or by a timeout (30s when push is available, 400ms when polling only) and then re-queries `events where seq > cursor` in batches of 200; on reconnect it deliberately fires an empty payload to make every subscriber catch up. The web client mirrors this with a snapshot carrying a `cursor` and ignores any reduction whose seq is older (apps/web/src/lib/thread-events.ts:141). Notifications are four kinds only — `completion | failure | help | takeover` (packages/adapter-kit/src/types.ts:450) — sent via `notifyRun` (executor.ts:2860) and only ever *after* the corresponding durable transition returned true (`if (!paused) return;`, `if (!completed) return;`), so the CAS that fires once is also what makes the notification fire once. The only user-facing gate is the per-bot `notifyOnFinish` boolean; "needs your approval / needs a code / needs an answer / needs you on the screen" are ungated. In-app progress narration is separately throttled to one event per 250 ms (executor.ts:2425). Nothing in the codebase polls external state without the model: the background jobs are all clock-driven expiries (idle sandbox sleep in computer-idle.ts, takeover lease expiry in computer-control.ts, teaching expiry, history compaction), and the builtin tool list (packages/adapters/src/builtin-tools.ts) has `schedule_create`/`schedule_list`/`schedule_cancel` but no watch or monitor tool.

### Patterns worth taking

#### The timer is a hint; persisted rows are the schedule  ·  high value, small effort

**What.** Two independent paths can start the same work. A timer fires at the scheduled instant, and a separate reconciler loop (createJobReconciler, 30s interval) sweeps durable state — runs that are queued or whose lease expired, routines whose nextRunAt is within 60s — and re-enqueues them. Losing every in-memory timer costs at most 30 seconds of latency, never a missed run.

**Why it beats the obvious alternative.** The obvious alternative is a durable queue: make the timer itself survive restarts. That forces a real store for the queue and still leaves the queue and the domain state able to disagree. Here the queue holds no authority at all, so it can be pure in-memory timers, which is exactly the constraint a dependency-free Mac app is under. It also makes the sweep the single recovery path for crash, quit, sleep, and a bug that dropped a timer — one mechanism instead of four.

**For us, in Swift.** Give Store a `sweep()` that reads persisted Routine and Run records and starts anything due or stale. Call it from a `Timer.publish(every: 30)` on the main actor, from `applicationDidFinishLaunching`, and from `NSWorkspace.shared.notificationCenter` observing `didWakeNotification` — sleep is the Mac's version of the worker dying. Timers set with `DispatchQueue.asyncAfter` do not fire while the machine is asleep and drift when it wakes, so the sweep is not an optimisation here, it is the load-bearing path.

#### nextRunAt as a claim token  ·  high value, small effort

**What.** `wakeRoutine` fires only if the routine's stored `nextRunAt` still equals the instant named in the wakeup payload, and it claims by conditionally updating that same field. Duplicate wakeups for one slot collapse to a single run because only the first update matches. The recomputed next occurrence uses `max(now, scheduledAt)`, so a slot missed while the machine was off fires once and the schedule resumes from the present.

**Why it beats the obvious alternative.** The alternative — dedupe on "did I already run this minute" — needs a separate ledger and gets the sleeping-laptop case wrong in both directions: either a week of missed daily runs all fire at once on wake, or the overdue run is silently skipped. Making the scheduled instant itself the claim token gives exactly-once firing and sane catch-up from one field.

**For us, in Swift.** Store `nextRunAt: Date?` on the routine and have the fire path take `scheduledFor: Date`, bail unless `routine.nextRunAt == scheduledFor`, then write the recomputed next date before creating the run. Under Store's single-writer rule this is trivially atomic, but keep the guard: it is what makes the wake-from-sleep sweep and a stale timer safe to both fire.

#### Deadlines enforced lazily on read, timers only for timeliness  ·  high value, small effort

**What.** Every expiring thing — a takeover lease, a teaching session, an execution lease — stores an absolute `expiresAt`, and every read path recomputes expiry from that timestamp (teaching-session.ts checks `expiresAt <= Date.now()` at four separate read sites). The background expiry job does the same thing eagerly so the UI updates without someone looking.

**Why it beats the obvious alternative.** It means a missed timer degrades timeliness, never correctness. For a laptop that closes mid-run this is the difference between "the lease looks alive because nothing fired to kill it" and "the lease is dead because the clock says so." It also removes the need for the timer and the state to be transactionally consistent.

**For us, in Swift.** Make expiry a computed property, never a stored flag: `var isActive: Bool { expiresAt > .now }`. Never write `state = .expired` from a timer as the only way expiry happens. This matters most for the permission side of Bot-Harness — a time-boxed grant must read as revoked after a sleep even though nothing ran to revoke it.

#### One job identity string that means dedupe, debounce, and cancel  ·  high value, small effort

**What.** Every background job carries an optional `replaceKey` (`routine:<id>`, `computer.sleep:<id>`, `history.compact:<threadId>`). Enqueueing with a key replaces any pending job with the same key; `cancel(key)` drops it. That one field gives idempotent re-enqueue from the reconciler, trailing-debounce for idle timeouts (`touchRunningComputer` re-arms the sleep job on every touch), and cancel-on-delete for routines — see InMemoryJobQueue in wakeup.ts, which implements all of it in about fifteen lines with a `Map<String, Timer>`.

**Why it beats the obvious alternative.** Without it, each of those three behaviours becomes its own bespoke bookkeeping, and the reconciler cannot safely re-enqueue what the timer already scheduled. The whole "timer is a hint" design depends on enqueue being idempotent, and this is the cheapest way to get it.

**For us, in Swift.** A `Scheduler` actor holding `[String: DispatchSourceTimer]`, with `schedule(key:at:work:)` cancelling any existing entry for the key and `cancel(key:)`. This is the entire replacement for Graphile Worker, and it is the natural place to also hang the idle-timeout behaviours Bot-Harness will want (auto-releasing screen recording, closing a shell session after inactivity).

#### Notify only after the state transition committed, and only on the two edges that matter  ·  high value, small effort

**What.** There are four notification kinds and no others: `completion`, `failure`, `help`, `takeover`. Each `notifyRun` call sits immediately after a conditional write that returned true — the run genuinely moved to paused-for-input, or genuinely finalised. The user-facing setting (`notifyOnFinish`) gates only the end-of-run pair; the three "the agent is blocked on you" cases are never suppressed. Streaming progress is a different channel entirely, throttled to one event per 250 ms.

**Why it beats the obvious alternative.** Anti-spam here is structural rather than a rate limiter: because the transition is a compare-and-swap that succeeds once, a retried or duplicated execution cannot produce a second notification, and a notification can never describe a state the record does not show. And the taxonomy encodes a real rule — interrupt the person when the agent cannot proceed without them, let them opt out of everything else.

**For us, in Swift.** Post through `UNUserNotificationCenter` from exactly the code path that just committed the state change, never from a general event observer, and never before the write. Keep the four kinds. Given Bot-Harness's autonomy/urgency contract, map only "blocked on the user" to an interrupting notification and let urgency decide whether completion notifies at all.

#### Push as a wake signal over a cursor-replayed durable log  ·  high value, medium effort

**What.** The realtime channel carries `{topic, payload}` but consumers never trust it for data — malformed signals are dropped with the comment that durable events remain in the database, and on reconnect the fanout deliberately delivers an empty payload to force every subscriber to catch up. `followThreadEvents` waits on a `ChangeLatch` woken by either the signal or a timeout, then re-reads `seq > cursor` in batches. The client snapshot carries the same cursor and discards any update older than what it holds.

**Why it beats the obvious alternative.** It collapses live updates and crash recovery into one code path. Reconnect, cold start, a dropped notification and a missed batch are all just "read from my cursor," so there is no separate replay path to get wrong. The two timeouts (30s with push, 400ms without) are the only thing that differs between a push and a polling deployment.

**For us, in Swift.** Bot-Harness already has the hard half: the append-only hash-chained trace is the durable log. Add a monotonic sequence per run, have views hold `lastSeq`, and make the in-process publisher (a Combine subject or an AsyncStream) send a bare "something changed" tick rather than the payload. Views re-read the trace from their cursor. Restoring a window after a relaunch then needs no special case, and the trace stays the only source of what happened.

#### The agent schedules itself, through the same object the user edits  ·  high value, medium effort

**What.** `schedule_create`, `schedule_list` and `schedule_cancel` (builtin-tools.ts:353) let the model create a routine from chat. `resolveScheduleTiming` in schedule-tools.ts accepts either a repeating form (`cron`, or `every`+`unit`) or a one-shot form (`runAt`, `delayMinutes`, `delaySeconds`), rejects supplying both, enforces a one-minute floor, and returns a validated cron plus a concrete `nextRunAt`. A "remind me in ten minutes" and a "every weekday at 9" become the same row, visible and editable in the Routines UI. The API refuses to let the UI create an active one-shot — those must come from chat — and refuses to re-arm one that already ran.

**Why it beats the obvious alternative.** The alternative is a separate reminders feature that the user cannot inspect and the agent cannot manage. Unifying on the sentinel cron means one storage model, one firing path, one list view, and the reminder the agent set for itself is something the user can see and delete. The validation living in a pure function, separate from persistence, is what lets the same rules serve the tool call and the form.

**For us, in Swift.** A `Routine` value with `crons: [String]` where `"@once"` is a legal entry, a pure `resolveScheduleTiming` returning `Result<(cron: String, nextRunAt: Date), ScheduleError>`, and three tools in the existing registry. Use `Calendar`/`DateComponents` with a stored IANA `TimeZone` identifier rather than writing a cron parser — a five-field parser is only needed if you want to accept raw cron from the model, and the `every`+`unit` form covers most of it.

### Not applicable to us

- Graphile Worker itself. What it buys them over the in-memory driver is job durability across a worker restart, multiple worker processes competing for one job, and retry/backoff bookkeeping. In a single-user Mac app with one process, the reconciler already covers restart, and there is no second consumer to coordinate with. The minimum viable equivalent is genuinely `InMemoryJobQueue` from wakeup.ts — a dictionary of keyed timers — plus the periodic sweep.
- createPostgresReconciliationLeadership (job-reconciler.ts). A session-scoped `pg_try_advisory_lock` that elects exactly one reconciler among N workers, with followers retrying each interval. Pure multi-process coordination; there is nothing to elect in one app process.
- PostgreSQL LISTEN/NOTIFY as transport, and the 7,900-byte payload ceiling it forces. The pattern it embodies (signal, not data) is worth taking; the transport is not. In-process this is a Combine subject or an AsyncStream.
- Keyset-cursor pagination and batchSize 100 inside the reconciler sweep, with per-scan cursors for runs, routines and control leases. That exists so one sweep cannot stall on a workspace with thousands of due rows. A single user will have tens of routines; a plain filter over the array is correct and the cursor machinery is the most complex part of that file.
- The inbound webhook (apps/api/src/webhook.ts): a bearer-authenticated HTTP endpoint per bot, which prepends the prompts of every `webhookEnabled` routine to the payload so an external event runs those routines. Opening a listening socket on a personal Mac to trigger an agent with real permissions is a poor trade. The two ideas worth lifting from it are the idempotency key hashed into a `clientNonce` with a uniqueness constraint on the run, and the notion of a routine that has no schedule and fires only on an event — where the events for us are local: FSEvents, NSWorkspace app launch/quit, NSMetadataQuery, calendar alarms.
- ExpoPushProvider — a POST to exp.host with a device token read from a file. Replaced entirely by UNUserNotificationCenter. Only its four-kind `NotificationMessage` shape transfers.
- The multi-tenant scoping that runs through every query (`workspaceId`, `userId`, `IsolationError`) and the `Attempt` table recording each leased attempt separately. The attempt log is arguably interesting as an audit record, but Bot-Harness's hash-chained trace already covers that ground better.

### Surprises

- There is no monitor or watcher anywhere in the product. Nothing polls an external resource and compares it to a previous value; there is no `watch` tool in builtin-tools.ts. Every always-on behaviour is either a clock deadline (routine fires, lease expires, sandbox goes idle) or an inbound webhook. "Tell me when this page changes" is answered by scheduling a routine that re-runs the model every N minutes and paying for it each time. If Bot-Harness wants a cheap monitor — hash a file, diff a page, watch a directory — there is no prior art here to copy, and building one that runs without calling the model would be a real differentiator rather than a port.
- `Routine.notify` is a dead field. It is in the schema (schema.prisma:532), accepted by routines.create and routines.update, returned by mapRoutine, and rendered in the editor — but no code path reads it when deciding whether to notify. The only gate the executor consults is `bot.notifyOnFinish`. A per-routine notification toggle that silently does nothing is exactly the kind of thing to check for before copying a schema.
- The Electron desktop app runs none of this. apps/desktop/src/main.ts is a window shell with auto-update and OAuth callback handling; routines, the reconciler and the worker all live server-side. So the repository's own desktop client is not an example of a local-first always-on agent — for Bot-Harness the entire mechanism has to move in-process, and this codebase has no version of that to imitate.
- Scheduling depends on exactly one third-party package, `croner`, and it is used only to answer "when is the next occurrence." Everything else in packages/core/src/cron.ts — presets, humanised descriptions, round-tripping a cron string back into a UI preset — is hand-written string work. And the one-shot case does not use croner at all: `"@once"` is a sentinel that never reaches a parser.
- Two independent producers routinely enqueue the same wakeup for the same routine (the reconciler's 60-second lookahead and the previous run's own re-enqueue), and this is deliberate rather than a bug, because `replaceKey` collapses them and the `nextRunAt` compare-and-swap makes a double-fire impossible. The design assumes duplicate triggers as the normal case instead of trying to prevent them.
- A run that is waiting on the user (`waiting_input`, `waiting_takeover`) is a fully parked durable state with no process attached and no lease held — the worker exits. Resumption is just another `run.continue` claim, and the model is told what happened through a short prompt note built by `takeoverResumeFromRelease` ("The user skipped the login. Continue without treating the login as complete. Do not request takeover again unless you still cannot proceed."). A multi-hour task blocked on a human costs nothing while it waits.
- The follow loop keeps polling even when push is connected — the latch simply uses a 30-second timeout instead of 400 ms (`PUSH_CATCH_UP_MS` vs `POLL_ONLY_CATCH_UP_MS` in db/src/events.ts). Push is treated as a latency optimisation on a polling loop rather than as a delivery mechanism, which is why a dropped notification is not a bug class here.
- Their agent-facing docs are a single 10-line AGENTS.md of flat prose rules, with CLAUDE.md containing literally one line: `@AGENTS.md`. No per-directory docs, no ADR log, no research index. Compared with our docs/PRODUCT.md plus docs/decisions/ plus docs/guides/ENVIRONMENT.md, they carry far less agent-facing context — but the one convention worth stealing is the single-file source of truth with CLAUDE.md as a pointer, which removes any chance of the two drifting apart.
