## Recommended stack

Brain: Claude via the raw Messages API with computer_toolset_20260801 — default claude-opus-5 at effort high, claude-sonnet-5 as the cost fallback for GUI grinding, model ID in config. Justification: it is the only stack with a macOS-native reference implementation (claude-quickstarts/computer-use-best-practices) that already solves screenshot resizing and click-coordinate alignment, and Kunal is a Claude Code power user with zero Gemini keys — the brief's Gemini choice buys a second divergent SDK surface, a docs-only desktop path, and an executor he would have to write anyway. Gemini becomes a config-swappable adapter in v2, not v1.

UI shell: native SwiftUI, signed with the existing Apple Development identity (224FA75C1E159B4B50EE901312F3B38632663F97), built by XcodeGen + xcodebuild with DEVELOPER_DIR pinned to /Applications/Xcode.app/Contents/Developer. Justification: verified on this machine — Xcode 26.6, SDK 26.5, Swift 6.3.3 are all present, so the brief's CLT-only constraint is fiction; and a stable signing identity is not polish, it is the only thing that keeps Screen Recording and Accessibility grants alive across rebuilds.

Agent loop: own it, in a Python 3.12 sidecar provisioned by uv (not the system 3.10), spawned as a long-lived child of the Swift app speaking newline-delimited JSON over stdio. Justification: the Agent SDK cannot reach computer use in -p mode, so the loop has to sit on the Messages API regardless; owning the loop is a few hundred lines and buys the per-step audit record that is this product's actual reason to exist.

OS-control layer: write it yourself in Swift — ScreenCaptureKit for capture, CGEvent for input, foreground control that the user watches. Justification: this is where I disagree with two tracks. cua-driver's background control is genuinely the better end state, but it rests on undocumented private SkyLight SPIs, drops right-clicks on Chromium content, fails outright on canvas apps, and requires granting the two most invasive TCC permissions to a third-party binary Kunal did not build — which contradicts the entire signed-app trust story. For v1, an agent you can watch and interrupt is safer than one working invisibly behind your active window. Put the executor behind one Swift protocol so cua-driver drops in later as a "background mode" flag.

Browser layer: do not build one. Route web tasks to Claude in Chrome (GA since 2026-08-26, its MCP tools are already exposed in this session) or chrome-devtools-mcp over Chrome's 144+ consented opt-in. Justification: pixel-driving a browser through screen control is the most expensive and least reliable path available, and Chrome's own consent dialog becomes your permission UX for free.

Sandbox: two separate domains, honestly labelled. /usr/bin/sandbox-exec with a generated Seatbelt profile (verified present on 26.5.2, hardcode the absolute path) for every shell command; a hard approval gate plus an unbypassable deny list for GUI actions, which Seatbelt cannot touch at all. No Docker, no VM, no apple/container in v1 — the latter shipped 1.3.1 today patching six advisories including host-file reads.

Trace store: SQLite in WAL mode, single file, your own run/step/artifact/change_log schema with columns named after gen_ai.* attributes, screenshots content-addressed on disk and redacted before write. Justification: WAL gives multi-process readers (Swift shell + Python sidecar) which DuckDB structurally cannot; SQLite links from the macOS SDK with no package manager. Arize Phoenix via `uvx arize-phoenix serve` as an optional viewer, never as the store.

## Day-one slice

Free at least 20GB of disk, run `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`, confirm `xcrun --show-sdk-version` reports 26.5, and get an Anthropic API key. Then build exactly one thing end to end: a signed SwiftUI .app named Bot-Harness that completes a single task — "open TextEdit and type hello" — through one full agent step, and nothing more.

The slice, concretely. XcodeGen generates the project from a committed project.yml; xcodebuild signs it with the Apple Development identity (never `--sign -`), and build.sh fails loudly if `codesign -d -r-` does not print `anchor apple generic`. On launch the app requests Screen Recording and Accessibility, and refuses to proceed until both are held. It captures one frame with ScreenCaptureKit using SCContentFilter's excludingApplications so it does not photograph itself, downscales it with the resize math ported verbatim from claude-quickstarts/computer-use-best-practices, and sends one Messages API turn with computer_toolset_20260801 and a cache_control breakpoint on the toolset. The returned action is rendered in the center pane as an approval card showing the model's stated intent and the exact action with no truncation — the OpenClaw CVE worth learning from is a confirmation dialog that elided what it was confirming. On Allow, and only on Allow, the Swift executor synthesizes one CGEvent click at the transformed coordinate. Then it captures a second frame and writes one row to SQLite in WAL mode carrying step index, intent, rationale, tool name, full arguments, the approval decision and who made it, the SHA-256 of both redacted screenshots, and the token split including cache reads.

Then quit the app, rebuild it, relaunch it, and confirm both TCC grants survived. That last step is not ceremony — it is the check that decides whether the next six weeks are pleasant or miserable, and it is the one thing in the whole research package that was reasoned about but never actually observed.

What this proves in one day: the toolchain is real, signing keeps permissions alive across rebuilds, capture works on macOS 26.5, the 0-999-to-Retina coordinate transform lands on target, the current toolset wire format is what the docs claim, the approval gate sits in the execution path rather than beside it, and the audit log records why as well as what. Every one of those is a genuine unknown today, and each one is cheap to falsify now and expensive to falsify in a month. No task list, no live-view pane, no browser layer, no Seatbelt, no MCP, no cua-driver, no Gemini.

## Contradictions found

- TOOLCHAIN — the two tracks flatly contradict each other and I resolved it by running both. `ui-ux-reference` says a Liquid Glass app 'literally cannot compile today' (SDK 15.2, Swift 6.0.3). `macos-native-app-stack` says Xcode 26.6 with the 26.5 SDK is installed. BOTH observations are correct and one conclusion is wrong. Verified: `xcode-select -p` returns /Library/Developer/CommandLineTools, so the DEFAULT toolchain is SDK 15.2 / Swift 6.0.3 — but /Applications/Xcode.app is Xcode 26.6 (build 17F113) carrying MacOSX26.5.sdk and Swift 6.3.3 targeting arm64-apple-macosx26.0. The ui-ux track compiled against the default and concluded impossibility. The fix is one command (`sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`), not an SDK download and not an architecture change. `macos-native-app-stack` wins.
- THE BRIEF'S CENTRAL PREMISE IS FALSE — 'Swift 6 CLT only, no full Xcode' is not this machine. Full Xcode 26.6 is on disk, XcodeGen 2.45.4 is installed, and a real Apple Development signing identity exists (224FA75C1E159B4B50EE901312F3B38632663F97, kunalbairwa232@gmail.com). Every constraint-driven workaround in the brief — hand-rolled build.sh, no asset catalogs, ad-hoc signing — is solving a problem that does not exist. Worse, ad-hoc signing would have been actively harmful: its designated requirement is a per-build cdhash, so every rebuild silently revokes Screen Recording and Accessibility, which are the only two permissions this product runs on.
- THE BRAIN — the brief specifies Gemini 3.7 Flash; no Gemini key is configured on this machine (verified: GEMINI_API_KEY unset). The `gemini-computer-use` track confirms the model and the desktop environment are real, but also confirms Google ships two divergent API surfaces that disagree with each other (docs teach `client.interactions.create` with dict tools; the official reference repo runs `client.models.generate_content` with typed constants), no macOS executor, no end-to-end example of the desktop path, and a stale README naming a model ID (gemini-3.6-flash) that appears nowhere in the docs or pricing. Meanwhile `claude-computer-use-and-agent-sdk` found a macOS-native, no-Docker reference implementation (claude-quickstarts/computer-use-best-practices) that already solves screenshot resizing and coordinate alignment. The brief picked the harder brain for no stated reason.
- OS-CONTROL PARADIGM — two tracks each declare a different thing 'the single highest-value finding', and they are incompatible paradigms, not complements. `grokbot-and-hermes` and `cua-desktop-control` both say adopt cua-driver: pixel/coordinate control posted per-PID via private SkyLight SPIs, no cursor movement. `openclaw` says adopt Peekaboo: accessibility-tree snapshot returning opaque element IDs, then act against those IDs — explicitly arguing this beats 'screenshot-and-guess-coordinates'. One is a pixel agent, the other is a semantic agent. Neither track acknowledges the other exists. Neither is installed (verified: no /Applications/CuaDriver.app, no peekaboo, no cua-driver on PATH).
- THE HARNESS RUNTIME — a genuine three-way split. `harness-engineering-patterns` says adopt claude-agent-sdk-python for its six-step permission pipeline and hooks. `agent-loop-architecture` says reject all frameworks and spawn `claude -p --output-format stream-json` from Swift. `claude-computer-use-and-agent-sdk` says the Agent SDK cannot reach computer use at all, because Claude Code's bundled computer-use MCP server is explicitly unavailable in `-p` mode — which invalidates the second option for the part of the product that matters and forces a raw Messages API path underneath either of the first two.
- BILLING — `claude-computer-use-and-agent-sdk` flags 'the single highest-value thing to test' as whether the SDK authenticates against the Max subscription; `harness-engineering-patterns` states flatly that Anthropic does not permit third-party products to offer claude.ai login and that Bot-Harness 'must use API key auth'. Verified: ANTHROPIC_API_KEY is unset on this machine. Computer use through the Messages API is not reachable today at any price. This is a hard blocker nobody put in a risks list.
- PYTHON VERSION — the brief and four tracks build reasoning on 'Python 3.10, exactly the minimum, zero headroom'. `browser-automation-layer` caught this and I confirmed it: python3 is 3.10.11, but /opt/homebrew/bin/python3.11 exists and uv is installed at ~/.local/bin/uv, which provisions any version on demand. The 3.10 ceiling is imaginary. `cua-desktop-control`'s claim that `pip install cua` will refuse to resolve is true of the system interpreter and irrelevant given uv.
- INFO.PLIST KEYS — `cua-desktop-control` states ScreenCaptureKit 'requires NSScreenCaptureUsageDescription in Info.plist or the system kills the app'. `macos-native-app-stack` grepped every binary under /System/Library and /usr/lib and found the string zero times, while the three genuine TCC keys appear twice each, and concludes the key does not exist and that adding it produces a dead entry plus false confidence that permissions are configured. The grep is the stronger evidence and I am siding with it, but this is unresolved and is a five-minute empirical test on day one. Same dispute exists for NSAccessibilityUsageDescription.
- GROK BOT'S IDENTITY — `grokbot-and-hermes` says 'built jointly by SpaceXAI and Cursor/Anysphere'; `ui-ux-reference` says it 'is not an xAI product' and found no evidence of an xAI-built cockpit. Verified: CFBundleIdentifier is com.anysphere.sand, the Developer ID signing authority is 'Anysphere Incorporated (DCNK4UB866)', and NSHumanReadableCopyright reads 'Copyright © 2026 SpaceXAI'. It is Cursor's client codebase under xAI copyright. The `grokbot-and-hermes` reading is right; `ui-ux-reference` overstated. Consequence for us: its layout is Cursor's layout, and its 'computer' is a remote VM with snapshot-and-reset, which is exactly the safety net a local Mac agent does not have.
- LAYOUT — the brief specifies left task list / center conversation / right live computer view / bottom action bar, sourced from Grok Bot. `ui-ux-reference` inspected the actual app and found none of that: left is a bot list, right is a Settings inspector, the computer opens from a title-bar icon rather than living in a pane, and status is a floating top-center pill. The brief's layout is real and good — it just comes from Manus, not from the app it claims to copy. Ship it, but stop citing Grok Bot as the source.
- MCP — `mcp-ecosystem` reports the protocol went stateless on 2026-07-28 (no handshake, no sessions, sampling/roots/logging deprecated) and the official Swift SDK is stranded a full spec revision behind with ten open SEP issues and no release since May. Three other tracks casually recommend 'wire it over MCP' from Swift as though it were a cheap boundary. It is cheap only from Node or Python, and only if @modelcontextprotocol/client 2.0.0 has actually implemented MRTR rather than just shipping the types — which that track explicitly could not confirm.
- THE PRODUCT MAY ALREADY EXIST — three independent tracks flag that Anthropic ships Claude Cowork (computer use on Pro/Max, macOS, per-app permissions, prompt-injection review) and shipped Claude in Chrome to GA on 2026-08-26, three days ago, whose MCP tool surface is already present in this very session. Anthropic's own best-practices README tells readers who want safeguards to use Cowork instead. The brief contains no positioning against either. This is the largest unexamined assumption in the whole package.
- DISK — no track checked, and it invalidates the first step of nearly every recommendation. Verified: 148Mi free on a 460Gi volume, 100% capacity. Bash tool calls are already failing with ENOSPC. Installing cua-driver, Peekaboo, Phoenix, Harbor, a second Python, or building anything is blocked right now.

## Open questions for Kunal

- Will you pay for an Anthropic API key, and what is the monthly ceiling? No key is configured, and computer use is not reachable on the Max subscription from a -p session. This single answer decides whether the brain is Opus 5, Sonnet 5, or a Gemini key you would have to go get — and it gates literally everything else.
- Does the agent need to work in the background while you keep using the Mac, or is watch-it-work acceptable for v1? Background control means depending on cua-driver's undocumented private Apple SPIs and handing Screen Recording and Accessibility to a third-party binary. Foreground control means you can see and interrupt it, but it fights you for the mouse. I recommend foreground for v1; tell me if that kills the product for you.
- What does Bot-Harness do that Claude Cowork and Claude in Chrome do not? Cowork already does macOS computer use on your Max plan with per-app permissions; Claude in Chrome went GA three days ago for your logged-in tabs. If the answer is 'the auditable decision trace and a local task queue', that is a real answer and it should reshape the UI to foreground the trace rather than the live view. If there isn't one, the cheaper bet is a shell that orchestrates those two.
- What is v1's blast radius: the whole Mac, or an explicit allowlist of apps and directories? There is no snapshot to roll back to on a local machine, so the answer sets how strict the default approval mode is and whether the deny list is a safety net or the primary boundary.
- Pixel-and-coordinates or accessibility-tree-and-element-IDs? Two research tracks each called their answer the highest-value finding and neither acknowledged the other. Coordinates match the Anthropic toolset natively and work everywhere; element IDs (Peekaboo's approach) are more reliable and produce a far more readable audit log but only cover apps that expose a good AX tree. I lean coordinates for v1 with an AX-tree assist for target disambiguation, but this is the deepest architectural fork in the project.

## Risks

- Nothing installs today. The disk is at 100% — 148Mi free of 460Gi — and Bash calls in this session already failed with ENOSPC. Every 'brew install', 'uv tool install', 'curl | bash' step across all fourteen tracks is blocked until this is cleared. This is the literal first task.
- There is no API key. ANTHROPIC_API_KEY is unset and computer use through the Messages API needs one; Claude Code's own computer-use MCP server is explicitly unreachable in -p mode, so the Max subscription cannot be routed around. Until a key exists and a budget is set, the brain does not run. Screenshot-heavy loops are input-token-dominated, so cost is driven by prompt caching and image pruning, not by reasoning — turn on cache_control over the ~4,500-token toolset definition and clear_tool_uses_20250919 with keep:3 on day one, or a single long session will be shockingly expensive.
- A local Mac agent has no undo. Grok Bot's 'reset the computer from a snapshot' has no equivalent here. The approval gate is doing all the safety work that a disposable cloud VM does for the reference product, which means it has to be stricter than the reference product's, not equally strict. Anthropic's own computer-use reference explicitly discourages running outside a VM and warns there are no safeguards against screenshotting sensitive information and uploading it.
- Prompt injection through the screen is unsolved and this product's threat model is the worst case. Anything visible — a web page, an email, a filename, a Slack message — is attacker-controlled input to an agent that also holds shell access on the primary machine. Anthropic's published residual rate is 3.8% for Opus 5 in Chrome with a classifier and probes; a hand-rolled harness has neither. Hard-code an unoverridable deny list (Keychain UI, System Settings, payment and credential fields, Terminal-in-Terminal) that no mode including a bypass mode can lift, and never let content read in one step silently authorize an action in the next.
- Screenshots are the leak vector and no tool solves it for you. Langfuse, Phoenix, OpenLIT and the OTel redaction processor all redact string attributes; none looks inside a PNG. One screenshot of a password manager or a terminal with an exported key is a plaintext credential at rest, and redaction after write is not redaction. This must be built into the capture path in Swift before the bytes hit disk, and there is no drop-in library for it.
- Anthropic may have already shipped this. Claude Cowork does computer use on Pro/Max with per-app permissions and an app blocklist; Claude in Chrome went GA three days ago for logged-in browser tabs. Both will keep shipping. Bot-Harness needs a differentiator that is not 'computer use on a Mac' — the honest candidates are the auditable decision trace, the local task queue, and native filesystem work, none of which Cowork foregrounds.
- Version churn is fast enough to invalidate this whole document. Anthropic's tool wire format moved computer_20250124 → computer_20251124 → computer_toolset_20260801 in about 19 months with a breaking shape change; MCP deleted its handshake and sessions on 2026-07-28; Chrome changed its debugging policy twice in eighteen months; ADK deprecated its orchestration primitives; OpenHands, OpenClaw, Peekaboo, Harbor and mcp-scan all renamed or changed owners. Isolate every version string, tool-type constant and beta header in one file, and expect to rewrite the adapter layer twice a year.
- TCC is fragile in ways that will eat days if not designed for. Grants attach to a bundle identity, need a full quit and relaunch, do not migrate from any earlier ad-hoc-signed prototype (stale entries must be manually removed or the toggle reads ON while access is denied), and reset when the Apple Development certificate expires in about a year. Note the expiry date now.
- Any agent or script that builds without setting DEVELOPER_DIR compiles against SDK 15.2 and SUCCEEDS, producing a binary that cannot use macOS 26 APIs. That is a silent-wrong-output failure, the worst kind, and it is the current default state of this machine. Fix it globally with xcode-select rather than per-shell exports, and put a guard in build.sh.
